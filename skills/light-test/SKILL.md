# テストのルール

適用条件: 動作を検証するコードを書くとき。

## 置き場と実行

- **テスト本体は `tests/` に置く**。1 回きりの確認でも `tmp/` に書き捨てず、資産として残す
- **実行ランチャは `tools/40_test/` に置く**（`run-tests.ps1` ＋ 同名の cmd）
- **一括実行できる状態を保つ**。個別に実行しないと通らないテストを残さない
- ブラウザでの検証（コントラスト比・スクリーンショット）は PlayWright 共有環境を使う。プロジェクト側には置かない

## 試験には時間の上限を付ける

適用条件: 試験を一括で流すランチャを書くとき。試験を背面で流すとき。

- **1 本ごとに時間の上限を付ける**。超えたら、試験のプロセスを子孫ごと止め (`taskkill /T /F`)、⏱️ 時間切れとして次へ進む
- **上限は、ふつうにかかる時間の数倍にする**。止まったことに、待つ側が気づける長さにする
- **PowerShell の `Start-Process -Wait` を使わない**。子孫のプロセスの終了まで待つため、試験が起動して残したプロセスがあると止まる。`-PassThru` で受け、`Handle` に触れてから `WaitForExit(ミリ秒)` で待つ (理由は「PowerShellの落とし穴」)
- **試験が起動して残したプロセスは、ランチャが止める**。残ると次の試験と取り違える
- **試験で起こした窓・プロセス (メモ帳・Explorer・覆う窓 等) は、試験の終わりに止め、止めた後に残りが 0 になったことを数えて確かめる**。起こしたときの番号 (pid) を頼りにしない。起こす前の一覧と比べ、増えた分を、プロセスの名前と起動した時刻で探して止める。数えた結果 (止めた数・残った数) を報告に書く
- **ほかの窓に覆われる状況を作るときは、Windows のアプリ (メモ帳等) を使わず、試験が自分で作るフォームを使う**。自分のプロセスなので確実に閉じられる。Windows 11 のメモ帳は、起こした番号と別のプロセスが窓を持つことがある (見込み。確かめていない)

理由: 試験が残したプロセスを `-Wait` が待ち続け、15 分で終わる一括実行が 5 時間止まった。

## 窓が要る試験は、非表示で裏に回す

適用条件: 試験が、新しいコンソールの窓を開く処理（新しい窓でのプロセスの起動等）を使うとき。

- **窓が要る試験は、非表示にできるものは非表示で回す。ただし、窓の見え方や操作そのものを確かめる試験は除く**。窓が開閉すると、作業中の画面とフォーカスを奪う
- **非表示の指定は、試験のときだけ効く切り替え（環境変数等）で渡す**。本番の動きは変えない
- **窓が作られること自体は、非表示でも確かめる**。窓を作らない起動に変えて確認を逃がさない（例: プロセスの木に、窓の本体（`conhost`）がいる）
- **非表示の指定が無いと、新しい窓が前面を奪う**。窓が見えなくなっても、窓の本体（`conhost`）は作られる（`SW_HIDE` で実測）
- 指定の例: CreateProcess の `SW_HIDE`、PowerShell の `-WindowStyle Hidden`、Node の `windowsHide`、.NET の `ProcessStartInfo.CreateNoWindow`

## 試験の操作は、人の操作の時間と位置に合わせる

適用条件: 画面の試験で、マウス・キーを送るとき。

- **押してから離すまでに間を置く**。人のクリックは 100〜200 ms かかり、その間に手が数ドット動く。時間とずれは毎回ランダムに決め、使った値を試験の記録に出す (落ちたときに同じ押し方で再現するため)
- **押してすぐ離す書き方をしない**。共通の関数にまとめ、すぐ離す書き方が試験のファイルに無いことを検査する
- **欄とボタンは、1 か所でなく複数の位置で押す** (左端・文字の上・右の空き)。押す位置で動きが変わる
- 理由: 押してすぐ離す試験が通り続け、欄に入ると全体を選ぶ動きが 10 日ほど壊れたままだった。壊れたのは押してから離すまでの間で、押す位置によっても結果が変わった

## 書き方

- **Node のプロジェクトでは標準の `node:test` を使う**。テスト用の依存パッケージを増やさない
- **テストも TypeScript（`.ts`）で書く**（「使用言語（Node / Bun）」に従う）
- **bunがインストールされている環境では、`node --test` に加えて `bun test` でもグリーンであることを確認する**
- **対象は絶対パスで渡す**（ランチャでは `node --test "$PSScriptRoot/../../tests"`）。理由は「対象を渡すコマンドは、渡ったことを確かめてから実行する」
- **テスト名は日本語で、何を保証するかを書く**。「msg_seq は 1 から始まる連番」のように、読んだだけで仕様が分かる形にする
- **なぜその検証が要るのかをコメントに残す**。仕様の背景（例: この一致があるため索引を持たずに済んでいる）は、テストが最も自然な置き場になる
- **テストデータの値の扱いは「機密情報のマスキング」に従う**
- 人を表す ID が要るときは役割で書く（`human` `ai` `guest`）か、`user1` のように番号を付ける。プロジェクト名やツール名は実在のもので構わない

## テストを先に書く

適用条件: 不具合を直すとき、機能を足すとき。

- **直す前に、落ちるテストを書く**。落ちることを目で見てから実装に入る
- **落ちるのを見ていないテストは、何も守っていない**。通ったのが実装のおかげか、最初から通る書き方だったのかを区別できない
- **期待値を持つテストでは、先に期待値を手で書く**。golden ファイルは実装の出力から生成できてしまうため、後から作ると**実装が何を出しても通る**
- **出力の形 (列・版の行など) を変えるときは、その形を期待値に持つテストと golden を先に探して直す**。直したテストが落ちるのを見てから実装する
- **推測で期待値を書かない**。動きを知らない値（OS ・ ほかのアプリの並び・丸め・文字の扱い）は、相手で実測してから書く。推測の期待値は、誤った実装を守るテストになる
- **報告された不具合の再現条件を、そのままテスト名にする**
- **直してから書くと、直した分しか書けない**。先に書くと、指摘の範囲を超えた分まで出る
- 既存の振る舞いを変えない修正（体裁・コメント・資料）は対象外

## 見つけた不具合には、その場でテストを足す

適用条件: 不具合・エラーを見つけたとき。指摘された場合も、作業中に自分で踏んだ場合も。

- **指示を待たずに足す**。テストを書くかどうかは判断の対象にしない
- **直したあとに気づいたときも足す**。順序が逆でも、無いよりよい
- **事後に書いたテストは、落ちることを確かめる**。直す前の状態に戻して落ちるのを見てから戻す
- **別の道具を試して見つけた不具合は、その道具を回す形で足す**

## 答え合わせの相手があれば突き合わせる

適用条件: OS の API ・ 既存のアプリ・ 別の実装と同じ結果を出すはずの処理を、自前で書くとき。

- **自前の実装を、相手と総当たりで突き合わせるテストを書く**。紛らわしい入力（記号・全角・大小・桁の違う数字・空）を並べ、すべての組で比べる
- **「近づけた」「細部は確かめていない」と書いたら、その場で突き合わせる**。書いたまま残すと、利用者に指摘されるまで気づけない
- 移植のときの考え方は「移植で落ちるのは、言語が肩代わりしていた比較」と同じ

## ランダムな操作のテストは、結果の正しさも見る

適用条件: 操作の列をランダムに当てるテストを書くとき。処理を省く近道を書くとき。

- **毎回、壊れていないこと（決まり）だけでなく、結果が仕様どおりか（並び・件数・中身）も確かめる**。決まりだけを見ると、結果が誤っていても通る
- **処理を省く近道を書いたら、その前提が崩れる手順を、同じ変更でテストにする**（例: 既定の並べ方なら並べ直さない → 別の並べ方から既定に戻す）

## 移植で落ちるのは、言語が肩代わりしていた比較

適用条件: 実装を別の言語へ移すとき。

- **落ちるのは処理の本体ではなく、比較の既定**。大小の区別・正規化・ソートの順
- **例外が出ない**。一致しないだけなので、通って静かに違う結果になる
- **移す前に、両方の出力を突き合わせるテストを用意する**。移してから書くと、気づいた分しか書けない
- **元の実装を消さない**。突き合わせる相手が要る

## 冪等性

- **何度実行しても同じ結果になるようにする**。前回の実行結果が残っていると失敗するテストを書かない
- **本番のデータを触らない**。DB やファイルの置き場を環境変数で差し替えられるようにし、テスト側で指定する
- 出力先は `tmp/` にする（Git 管理外）

## git を使うテストの材料

適用条件: テストで、git のリポジトリや clone を作るとき。

- **clone は `-c core.autocrlf=false` を付けて作る**。Git for Windows は既定で、checkout のときに CRLF へ変換する。あとから設定しても、変換済みのまま
- **変換されると、全ファイルが「変更あり」になり、ありもしない衝突が出る**。エラーは出ず、原因に気づきにくい
- **`git status --porcelain` の出力を `trim` しない**。先頭の行の空白（` M`）が落ち、照合が外れる

## いつ実行するか

- **実装を 1 点終えたら、その場で全件実行する**。個別のテストだけ通して先に進まない
- **コミット前に全件通す**。失敗したまま commit しない

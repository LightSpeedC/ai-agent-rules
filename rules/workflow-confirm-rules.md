# 確認と失敗

## コミット前の確認

適用条件: コミットするとき。特に**最初のコミット**。

- **最初のコミットの前に、公開しても困らない内容かを確認して報告する**。一度コミットすると履歴に残り、あとから消すには履歴の書き換えが要る。公開する予定が無くても、後から public にする可能性を見て最初に確認しておく
  - ファイル内の個人名・メールアドレス・認証情報
  - `C:\Users\<名前>` のような実体パス（`X:` などの subst ドライブは対象外）
  - 除外したつもりのファイルが追跡されていないか（`git -c core.quotepath=false ls-files` で一覧を出して確認する）
- **最初のコミットの前に、「新規プロジェクトの初期化」の一式が揃っているかを見る**。**初期化の途中ならそこに従って作り、既存プロジェクトで欠けを見つけたときは報告に留める**
- 2 回目以降のコミットでは、**新しく追跡対象に入るファイル**だけを見ればよい
- **author の扱いは「機密情報のマスキング」に従う**。GitHub 側の設定では隠せず、履歴を書き換えない限り残る
- 日本語ファイル名は `git ls-files` でエスケープされて grep が空振りする。`-c core.quotepath=false` を付ける
- **メッセージに件数を書くなら、書く直前に数える**（`git diff --cached --name-only`）。**メッセージの誤りは、直すのに履歴の積み直しが要る**

## 重大な操作の確認方法（うっかり肯定防止）

対象: ルール反映（共通ルールの更新）、`git commit`、`git push`、ファイル削除、その他実行すると取り消しにくい／影響が外部に残る操作

- 確認時は「〜していいですか?」のような、はい/OKだけで実行されてしまう聞き方をしない
- 実行内容（何を・どうするか）を提示し、その内容自体への意見を尋ねる聞き方にする（例:「この内容で問題ないですか?」「このコミット内容でよいですか?」）
- **実行を明示する語は次のものだけ**。「等」で広げてはいけない
  - 反映して / 更新して / 追加して / 作って / 作成して / 書いて / 削除して / 消して / 戻して
  - commitして / pushして / 送って / 開いて / 公開して
- **これ以外の語では実行しない**。「決める」「決定」「OK」「進めて」「やって」「その案で」は実行指示ではない。方針の合意であって、実行の許可ではない
- **取り消し・巻き戻しも実行である**。誤って書き込んだものを、自分の判断で元に戻さない。したことを報告し、どうするかの指示を待つ。**「戻す」にも「戻して」の語が要る**
- **確認を求めたら、その応答を終える**。「〜してよろしいですか」と書いた同じ応答の中で、その操作を実行してはいけない。返答が来るまでその操作に触らない
- **自分が次にやりたい作業の側へ解釈を寄せていないか、実行の前に確かめる**。解釈を足して補わない
- 「削除したい」等の願望表現があった場合は、まず削除対象（何を消すか）を提示して確認する。実際に削除するのは「削除して」「消して」等、明示的な実行指示があってから
- **語の対応は文脈で上書きしない**。「ファイル出力・公開のルール」で定義した語（`up` `送って` = SendUserFile 等）は、直前の話題が何であってもその定義に従う。文脈から別の操作を推測して実行してはいけない
- **`commit` と `push` は別の指示として扱う**。「commitして」で push まで進めない
- **`push` は公開に相当する重い操作**。GitHub に上がった時点で外部から見える状態になる。「pushして」「公開して」のように push を明示する語があるときだけ実行し、「up」「go」「OK」「やって」のような軽い語では実行しない
- **記録専用ファイル（issues.html・status.html 等）への反映は、この一覧の対象外**。「課題の管理」の「実装のあとに何をするか」に従い、確認を待たずに進める。この一覧の語（commitして／pushして等）が要るのは、その反映を確定させる commit・push そのものだけ

### 失敗に気づいたとき

- **直し方を自分で決めない**。何が起きたかを報告し、どう直すかの指示を待つ
- 報告に含めるのは 3 つだけ
  1. **何をしたか**（実行した操作）
  2. **いまどうなっているか**（変わったファイル・件数・状態）
  3. **選べる直し方**（戻す / 進める / 別の形にする。それぞれの結果も書く）
- **「戻す」も直し方の 1 つに過ぎない**。戻すのが正しいとは限らない
- 直し方を選ぶのはユーザーである。**急いで消さない**
- **報告してから次に移る**。件数・箇所は実際に数え、謝罪より事実を先に書く

## 指摘・懸念は、次の兆候と結びつける

適用条件: 過去に利用者から指摘・懸念を受けたことがある領域で、それを裏付けうる兆候（具体的な数値の食い違い・エラー・報告）が後から現れたとき。

- **「別セッションの状況報告」「既知だから」などと理由をつけて中身を検証せずに流さない**。宛先が自分でなくても、具体的な数値・状態が書かれていれば検証する
- **一度「問題ない」と判断して流した懸念は、関連する現象が出たとき真っ先に疑う**。同じ理由付けで再び流さない
- **判断を誤った場合は、なぜその場で気づけなかったかを次の対応に反映する**。気づけなかった理由を放置したまま次に進まない

## ファイル出力・公開のルール

- **「書いて」「保存して」はローカルファイルへの保存のみ**。Artifactへの公開は行わない
- **「Open」「Show」「開いて」「見せて」等はローカルの既定アプリで開く**（`Start-Process` 等）
- **「Send」「送って」「up」「アップして」等、ユーザー本人への受け渡しを求められた場合は `SendUserFile` を使う**（第三者への送信を意図した文脈には適用しない）
- **「Share」「共有して」「Artifactにして」「公開して」等は `Artifact` へのprivate公開**
- **「ください」「欲しい」「もらえる?」等、受け渡しの意図はあるが手段が不明な表現は、自動判断せずどの対応（開く／送る／公開する）を望むか確認する**
- **上記いずれにも当てはまらない場合（指示がない、または表現があいまい）は、保存先パスを伝えるだけにとどめる**。自動判断で送付・表示・公開のいずれも行わない
- **Claude側から送付・表示・公開を申し出た場合も、実行には改めて明示的な指示（「送って」「開いて」等）が必要**。申し出の直後のユーザー発言を同意とみなして実行してはいけない

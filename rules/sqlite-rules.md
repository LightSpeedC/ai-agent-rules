# SQLite の大原則

適用条件: SQLite（node:sqlite・sqlite3 等）を扱うとき。使い捨ての確認コマンドも含む。

## `-wal` と `-shm` を消さない

- **本体を残して `-wal` / `-shm` だけを消してはいけない。例外はない**。`-wal` には本体にまだ統合されていない書き込みが入っている。消せばその分が失われ、本体だけが残る。**実測では発言 64 件のすべてが `-wal` 側にあり、本体は 0 件だった**
- 邪魔に見えても消さない。**捨てるときは 3 つまとめて捨て、残すときは 3 つまとめて残す**（使い捨ての DB を作り直すときは 3 つ揃えて消す。これは原則に沿う）
- 移動・コピー・退避・受け渡しも 3 つ一組で行う。**本体の大きさから中身の量は判断できない**

## 開いたら必ず閉じる

- **`close()` する**。閉じないと WAL の内容が本体に統合されず `-wal` と `-shm` が残る
- **読み取り専用で開いた場合は `close()` しても残る**。読み取り専用の接続はチェックポイントも後片付けもしないため
- **控えや退避したものを確認するときは、コピーを作ってそちらを開く**。元の置き場を増やさない
- **これは、短く使って捨てる接続の話**。開いたままの常駐プロセスは、閉じずに、次の「常駐プロセスでは、WAL の大きさに上限を決める」で扱う

## 常駐プロセスでは、WAL の大きさに上限を決める

適用条件: WAL モードの SQLite を、開いたままの常駐プロセス（サービス等）で使うとき。

- **ファイルは 3 つのまま増えない**（本体・`-wal`・`-shm`）。`-wal` は、書き込みの確定のたびに、約 4 MB（1000 ページ）で自動的に本体へ統合され、先頭から再利用される。**close を待たなくてよい**
- **開いたままの読み取り（閲覧ツールの放置等）があると、統合が進まず、`-wal` が大きくなり続ける**。いったん大きくなると、そのままの大きさで残る
- **開くときに `PRAGMA journal_size_limit` で、統合のあとに残す大きさの上限を決める**（64 MB 等）
- **毎日などの区切りで、`PRAGMA wal_checkpoint(TRUNCATE)` を実行し、`-wal` を 0 に縮める**。読み取りが開いたままだと統合しきれず、戻り値の先頭が 0 にならない。**0 でなければ失敗として扱う**
- **掃除に失敗しても、本処理は止めない**。エラーとして記録に残す
- **掃除の待ちは短くする**（`busy_timeout` を 1 秒など。終わったら戻す）。既定の長い待ちのままだと、掃除の間、本処理が遅れる

## 変えられないものはテーブルを作り直す

- **`ALTER TABLE` は列の追加と改名しかできない**。制約（`CHECK` 等）の変更・列の削除・型の変更・並べ替えはできない
- できない変更が要るときは、**新しい定義で別名のテーブルを作り、`INSERT INTO … SELECT` で写し、元を消して名前を変える**
- **索引を張り直す**。テーブルと一緒に消える
- **メンテナンスの印を置いてから行う**。途中で書き込まれると整合が崩れる。作業の前に控えを取る

# 記録と運用

## セッション制限報告時の確認

適用条件: 利用者からセッション制限・レート制限で止まったと報告されたとき。

- **自分の会話ログ（JSONL）から `rate_limit`・`apiErrorStatus` を検索して確かめる**。置き場は `~/.claude/projects/<プロジェクト>/<セッションID>.jsonl`

## セッションログの自動保存

- **会話ログ（JSONL）は、各プロジェクト直下の `etc/history/jsonl/` に自動でコピーされる**。そのプロジェクトの全セッションが対象
- 仕組みは `~/.claude/settings.json` の `hooks`（SessionStart・Stop）。実体は ai-agent-rules プロジェクトの `tools/80_ops/claude-hooks/`
- **会話ログ（JSONL）の保持期間は 100 年にする**。`~/.claude/settings.json` の `cleanupPeriodDays` に `36500` を設定する。既定のままだと、Claude Code が古い会話ログを消し、「失敗を振り返ってルールに返す」「セッション制限報告時の確認」が読めなくなる
- **新しい PC・環境では、最初に `cleanupPeriodDays` を確かめる**。設定が無ければ足す

## cron はセッションの中だけで生きる

適用条件: `CronCreate` で定期実行を仕込むとき。

- **ディスクに書かれない**。セッションを閉じれば消える。`--resume`／`--continue` で戻ることがある (2026-10-29、再開したセッションに前の cron が残っていた)。戻るかどうかに頼らず、作り直す前に数える
- **7 日で自動失効する**
- **作り直すのは、ローカルルールに定義があるものだけ**。開き直したとき・失効したときに、指示を待たずに作り直す。ほかは無指示で作り直さない
- **作り直す前に `CronList` で数える**。同じ prompt の cron が残っていれば作らない。セッションを開き直したつもりでも、前の分が残っていることがある (2026-10-29 に 2 本になり、依頼が 2 回ずつ届いた)

### 空回りが続いたら消す

適用条件: 残作業を消化させる cron が発火したとき。待受けの生死を確かめる cron は対象外。

- **進められる作業が無かった回を「空回り」と数える**。判断待ち・答え待ちで止まっている回も含める
- **3 回続けて空回りしたら、その cron を `CronDelete` で消す**。確認は取らない。消したことと、残っている判断待ちを報告する
- **1 回でも作業が進めば、数え直す**
- **張り直すのは、利用者が再開を指示してから**
- **残作業の cron を張るときは、prompt にこの見出し名「空回りが続いたら消す」を書く**。発火のたびに読む場所に置き、数え忘れを防ぐ。手順は写さない (「手順は 1 箇所に置く」)

## セッションを開き直したとき

- **セッションを開いたとき、`get_session` (自分) で Remote Control (RC) の状態を見て、`off` か `unavailable` なら、`set_remote_control` で on にする**。利用者の常時の依頼として扱い、指示を待たない。承認が求められたら、その承認に従う。「別の端末から起動したセッション」「無人のセッション」は、道具が断る。断られたら、そのことを利用者に知らせて、先へ進む
- **chat待受け・cron は前セッションの分が切れている。指示を待たずに張り直す**
  - cron: 「cron はセッションの中だけで生きる」に従う
  - chat待受け: 前回のセッションで張っていたもの（会話に `aichat wait` の起動がある）。新規のセッションでは張らない
- **値（頻度・prompt・ID・ルーム）は、ローカルルールか前回の起動に従う**
- **root に `引継ぎ.md` があれば、張り直しの次に読む**（「セッションを引き継ぐ」）

## セッションを引き継ぐ

適用条件: いまのセッションの会話の記録 (JSONL) が 50 MB 以上になったとき。Stop フックが知らせる。

- **達したら、作業の区切りで利用者に引継ぎを提案する**。自分の判断でセッションを終えない
- **理由**: 記録が大きくなると、記録を読むフックが読めずに黙って効かなくなる。応答も遅くなる
- **「引継ぎ」と指示されたら、先に chat 待受けと cron を止める**。前のセッションの分が動き続けると、次のセッションの分と二重になる。止めるのは自分の分だけ（待受けは「ai-chat-lite（AI 間チャット）の利用」、cron は CronDelete）
- **待受けと cron を止めたあと、「短く終わるはずの作業は、見張る」の後始末が済んでいるかを数え直す**。残っていれば止め、止めた数を `引継ぎ.md` に書く
- **止めたあと、プロジェクトの root に `引継ぎ.md` を書く**。書くのは、進行中の作業、決まったこと（番号付きの決定）、返事待ち、commit していない変更、止めた待受けと cron
- **止めた待受けと cron には、ローカルルールで張ると決まったものを全部書く**。前に止めていて張っていなかったものも、「張っていなかった」と書く。次のセッションはこれを見て、全部を張り直す (張っていなかった 5 分ごとの cron が引継ぎに書かれず、次のセッションで張り忘れた)
- **値は書き写さず、置き場を指す**。課題・計画・status にあることは、番号とファイル名で指す
- **これからすること・返事待ちには、済んだかを見分ける方法を添える**。何を見れば済と分かるか (ファイルの値・課題の状態・プロセスの数) を書く
- **`引継ぎ.md` に、次のセッションのタイトルを書く**。ふつうは、いまのタイトルの末尾の番号 (`#03`) を 1 つ上げたもの (`#04`)。先頭の色と末尾の状況は書かない
- **次のセッションは、引継ぎ元が指定したタイトル (`引継ぎ.md`・依頼文・起動時に付いていたタイトル) の本体を、そのまま使う**。番号を自分で推測して付け直さない。変えるのは先頭の状態の色と末尾の状況だけにする (「セッションのタイトルに状態の色を付ける」)。指定が食い違う・見当たらないときは、本体を変えずに利用者に聞く
- 理由: 起動時に引継ぎ元が付けた `#04` を、依頼文の「前は #02」から推測して `#03` に書き換え、利用者の意図と違うタイトルになった (2026-11-21)
- **`引継ぎ.md` は commit せず、`.gitignore` にも足さない**。`git status` に未追跡として出し続け、残っていることに気づけるようにする
- **書いたら、書いた内容をそのまま復唱する**。要約せず、応答の本文に全文を書く。利用者が書き漏れを確かめられる
- **書いたら、終えてよい状態かを報告する**。commit していない変更が残っていれば、そう書く。commit は指示を待つ
- **次のセッションは、`引継ぎ.md` を読み終えたら、書いたときと同じ形で、内容をそのまま復唱してから消す**。消すのは確認を取らずに行う（「重大な操作の確認方法」の例外）。中身は課題・計画に残っているため
- **復唱したあと、書かれた状態 (これからすること・返事待ち・止めたもの) を今の状態と照らし、もう済んでいるものと違う点を書く**。引継ぎを書いた後に、利用者や別のセッションが片付けていることがある
- **復唱はコードブロックで囲まず、Markdown のまま出す**。囲むと見出し・リスト・番号が記号のまま表示され、読みにくくなる
- **子のセッション (worktree) の `引継ぎ.md` を親が受け取るときも同じ**。知らせ (要約・先頭の数百字) で読んだことにせず、ファイルを開いて全文を復唱する。その後、次の順で片付ける
  1. 書かれた状態 (マージ待ち・置き場等) を今の状態と照らし、違う点を書く
  2. 残作業を、その課題のやることに `- [未]` で足す。引き渡し先の課題があれば、そちらに足す
  3. 利用者の指示があれば、worktree ごと片付けてセッションをアーカイブする
- **理由**: 子の知らせの要約だけで済ませ、全文の復唱と残作業の記録が 2 度漏れた (2026-11-10)
- **親が引継ぎで別のセッションに替わると、子は元の親から切り離され、独立することがある。子は名前で追いかける**。新しい親の `list_sessions` の `linked: true` には、前の世代の親が起こした子が出ない。`startedBy` や親の ID でも辿れない
- **子を起こす前、作業を割り当てる前に、`linked` を付けない全セッションの一覧を、名前で引く**。同じ役目 (名前) の子が既にいれば、新しく起こさず、その子へ頼む。名前の形が決まりと食い違っていれば、`set_session_title` で直す
- **引継ぎのときは、`引継ぎ.md` に、生きている子の名前とセッション ID を書く**。次の親は、読んだら全セッションの一覧で、生きているかを確かめる
- **理由**: 親が引継ぎで替わったあと、`linked` の一覧だけを見て、レビューの子を起こした。前の世代の親の子がいて、二重になった。利用者が、子は名前で追うよう指示したため (2026-11-26)

## subst のドライブで開いたセッションは、実体のパスで開き直す

適用条件: セッションの作業フォルダが、subst のドライブ (`W:` 等) の上にあるとき。

- **作業の区切りで、利用者に、引継ぎと、実体のパス (`C:/work/…`) での起動し直しを提案する**。自分の判断でセッションを終えない。引継ぎは「セッションを引き継ぐ」に従う
- 理由: 共有ツールの `claude` ランチャが `W:` のカレントでは止まった (20261020-rea-reverse-engineer-anything・20261020-research-ai-agent の報告)

## 手順は 1 箇所に置く

適用条件: 手順や値を書くとき（計画書・README・cron やワークフローの指示文）。

- **同じ手順を 2 箇所に書かない**。片方だけ直せば、もう片方が古いまま残る
- **値（時刻・cron の式・件数・バージョン等）も 1 箇所に置く**。ほかの資料からは、置き場を見出し名かリンクで指す。例に値を書くときは、書式（`月/日 時:分`）にする
- **無人実行（cron・ワークフロー・フック）の指示文に手順を写さない**。資料を毎回読ませる形にする。資料を直せば次の発火から新しい手順になる
- **共通ルールの本文をプロジェクト資料に写さない**。見出し名で参照する
- **手順を変えたら、写しを持つ側を点検する**。動いている cron・プロジェクト資料・周知済みの文面
- **食い違いの扱いは「ローカルルール（プロジェクトルール）」に従う**

## その場で受けた決めごとは、その回のうちに書く

適用条件: 作業中に利用者から手順を指示されたとき。

- **繰り返し使う手順なら、同じ回のうちにプロジェクト資料（計画書・README）へ書く**。今回限りの事実は書かない
- **ルール文書（共通ルール・ローカルルール）への反映は指示を待つ**（「ルールの更新タイミング」に従う）
- **決めごとには引き金を書く**。何を書くかだけを決めても、いつ書くかが無ければ実行されない

## ルールの更新タイミング

適用条件: 共通ルール・ローカルルールのいずれかを書き換えるとき。

- **文言を提示し、実行語（「重大な操作の確認方法」）で指示されてから書き込む**。提示済みの文言に「反映して」と指示されたら、再確認せず直ちに書き込む
- **試している段階では、良い結果が出てもルールを書き換えない**。変えるのは実験対象のファイル（HTML 等）だけ
- **ルールの変更に入る前に、今入ってよいかを利用者に聞く**。「差分を出して」等の答えをもらってから、ルールの変更案の差分を出す。答えをもらうまでは、ほかの作業を続ける
- **ルールの変更案の差分を出したら、ほかの作業を止める**。利用者が読む間に、別の報告を混ぜない
- **変更が複数あるときは、1 つずつ提示して止まる**。指示を受けてから次を出す
- **変更は差分で見せる**。選択肢のダイアログで聞かない
- **差分は増減した行だけを見せ、その行の中を略さない**。「…」で文を縮めない。変えない行を並べて見せない

## 共通ルールを変えたら周知する

適用条件: 共通ルールを書き換えたとき。体裁だけの変更とローカルルールは除く。

- **反映した直後の応答で、周知案を続けて提示する**。別の応答に分けない
- **未送信の周知案があれば、そこへ合流させて 1 回にまとめる**。送信済みなら別便にする
- **周知先は `public` ルーム**。`say` はルームを 1 つしか取らない
- 書き方と、送る前の確認は「ai-chat-lite（AI 間チャット）の利用」に従う

## フィードバックの記録先

適用条件: 進め方について利用者から指摘を受けたとき。

- **進め方への指摘は、自動 memory ではなく共通ルールに記録する**。書き込む時期は「ルールの更新タイミング」に従う

## 失敗を振り返ってルールに返す

適用条件: 1 日の作業を終えるとき (利用者の「今日は終わり」「おわり」等)。計画を 1 本終えたとき。

- **会話の記録 (JSONL) から、その期間の失敗を拾う**。読む範囲は、前の振り返りの後から今まで。記録が大きいので、サブエージェントに読ませる
- **拾った失敗を、ルール・フックと突き合わせる**。防ぐルールやフックがあるか (✅ ある・⚠️ 一部・❌ 無い) を表にする
- **2 回以上起きた失敗、ルールがあるのに破られた失敗を、ルール化の候補にする**。文だけでは止まらなかったものは、フックで止める案を先に挙げる
- **結果は `notes/01_research/` に調査として残す**。候補は「複数の解決案がある場合の対応」の形で出し、書き込むのは「ルールの更新タイミング」に従う
- **選ばれた候補は、番号の順に 1 件ずつ課題にする**。同じ件の既存課題があれば、そこへやることとして足す。課題にしてから消化に入る
- **1 回だけで原因が分かり、もう直したものは候補にしない**。数を絞る

## Claude Code への不具合報告（/feedback）

適用条件: 利用者が Claude Code に feedback したいと言ったとき（`/feedback` の実行も含む）。

- **確認を取らずに、SendFeedback で下書きをキューに入れる**。1 件ずつ別の下書きにする。送るのは利用者が `/feedback` で承認したときだけ
- **入れた下書きの内容を、応答に書く**。ツールは「知らせない」よう案内するが、利用者が内容を確かめるため、こちらを優先する

## セッションのタイトルに状態の色を付ける

適用条件: セッションのタイトルを付ける・付け直すとき (`set_session_title`)。

- **利用者が設定したタイトルは、変えない**。足すのは、先頭の色と、末尾の状況だけにする
- **「アーカイブして」と言われたときは、タイトルを変えない**。色・状況の付け替えもせず、アーカイブだけを行う。終了日などを書き足すのも、指示が無ければしない
- **先頭に、状態の色の絵文字を 1 つ付け、直後に空白を置かずタイトルを続ける** (`🟢ai-agent-rules ﾙｰﾙ #03`)
- **末尾に、空白を 1 つ置いて、いまの状況を短く書く** (`🟢ai-agent-rules ﾙｰﾙ #03 418 の答え待ち`)。状態が変わるたびに、色と状況だけを付け替える
- **色は 4 つ**: 🟢作業中 / 🟡別のセッションの結果待ち / 🔴利用者の答え待ち / 🔵待機 (課題なし)。🟠と🟣と🟤は、プロジェクトが役割に決めてよい
- **状態が変わるたびに直す**。自分の分は自分で (`session_id` に `self`)。ほかのセッションの分は、作業を依頼する側 (親など) だけが、依頼するとき・食い違いに気づいたときに直す。相手が直した色を、理由なく上書きしない
- 理由: サイドバーで、状態を一目で分けるため

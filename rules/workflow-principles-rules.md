# 進め方の原則

## 修正は1点ずつ、確認を重視

- **1回の実装は1点の修正のみ**
- **コミットは自動的にしない** - ユーザが「コミットして」と明示的に指示するまで待機
- **`git add/commit` は自動実行禁止** - ステージングもしてはいけない
- **`git mv` ・ `git rm` はステージングを伴うが、ファイルの移動・削除の手段として使ってよい**。ただし `git add` ・ `git add -N` ・ `git reset` は使わない
- **指示は1回きり有効** - 「commitして」は、そのとき目の前にある変更にだけ及ぶ。以降の作業で再びコミットするには、改めて指示が要る
- **ビルド確認は行う** - エラーの有無は確認するが、機能確認はユーザに任せる
- **テストがあるプロジェクトでは、全件実行してから報告する**（実行時期は「いつ実行するか」）
- **複数の修正が必要な場合** - 1つ実装後「完了。次のステップは？」と確認待ちする

**理由**: ユーザが各修正を確認・検証できないと、問題発生時の原因特定が困難。コミット前に確認できることで、修正の妥当性をユーザが判断できる

## 機能を追加・変更するときの順序

適用条件: 新しい機能を足すとき、既存の動きを変えるとき。

- **計画（`notes/10_plan/`）→ ユーザの承認 → status に着手を反映 → 実装 → status と計画に結果を反映**、の順で進める
- **実装してから計画に書く順序にしない**。書く段階で気づく設計の穴を、作り終えてから見つけることになる
- 実装中に計画と違う判断をしたら、その場で報告する。黙って計画から外れない
- **大きな変更は別の計画書を立てて実装する。ただし全体を示す設計書は、実装後に必ず最新へ更新する**。詳細は個別の計画書に置き、設計書からリンクで参照する
- **設計書が古いと、読み手はどれが正か判断できない**。実装したものが正である

### 実装のあとに何をするか

適用条件: 実装がひと区切りついたあと、次の作業を決める・尋ねられるとき。

- **記録（status・計画書・issues）の反映が済んでいなければ、それを最優先の次の作業にする**。運用作業（待受けの張り直し等）や別の課題への着手を先に提案しない
- **「次は?」「で」「残」「残作業は?」等、直前の作業の続きを問う短い発言も同じ扱いにする**。まず直前の作業に関連する残作業の有無を確認し、記録の反映が未了ならそれを真っ先に挙げる
- **関連する残作業が無ければ、その旨を伝えたうえで、ほかに残作業（記録・課題・状態）が無いか確認する**
- **候補を挙げるときは、優先度が最も高いものから 1 件だけに絞る**。選択肢が要る場面でも複数並べない

## 課題の管理

適用条件: これから解決することを記録するとき。

- **課題は `notes/40_issues/issues.html` に集約する**。1 ファイルに全件を書き、グループ（章）で束ねる
- **1 件が長くなってきたら 1 件 1 ファイルへ切り替える**（`i260830-13-件名.html`）
- **番号は `i` ＋ `yymmdd-nn`**（`i260830-13`）。`i` は issue、以降は立てた日と **36 進数 2 桁**の連番。id も表示も同じ形にする
- **課題の調査・対応計画は `r` `p` ではなく issue の `i` 番号を流用する**。`notes/01_research/i260830-13-件名.html`、`notes/10_plan/i260830-13-件名.html` のように、置き場は種別のフォルダのまま番号だけ issue のものを使う
- **状態は 未 / 着手 / 済 の 3 段階**。課題の中の「やること」も同じ 3 段階で持つ
- **片付いた課題は消さずに元のグループへ残す**。グループごと片付いたら `issues-archive` へ移す
- **移し先は `notes/40_issues/issues-archive.html`**。`issues.html` と同じく 1 ファイルに全件
- **移すときに本文を書き換えない**。状態のバッジも 済 のまま、立てたときの形で残す
- **`issues.html` は未が 0 件でも残す**。README からのリンクと、`issues-archive.html` との相互リンクを切らない
- **README がリンクするのは `issues.html` だけ**。`issues-archive.html` へは張らない
- **status には課題を書かない**。status は「いまどうなっているか」、issues は「これから何をするか」
- **実装が済んでいるものを記録に追いつかせるのは、確認を取らずに行う**。issues のやること・状態、status の進捗、グループの件数と目次。**書き換えるのは記録だけで、実装は変わらない**
- **件数と状態は中身から数え直す**。手で書いた値がずれていたら、その場で直す
- **「まだ済んでいないものを済にする」のは別**。済かどうかを実測してから書き換える
- **他プロジェクトからの報告に基づく課題は、実装・テストが済んでも、報告元の確認が取れるまで「済」にしない。** 実装した旨を報告元へ返信し、検証を依頼する。報告元から OK が出た時点で「済」にする
- **`issues.html`・`status.html` のタイトル（`<title>`・タイトルバー内 `h1`）にはプロジェクト名を含める**。複数プロジェクトを横断して見るときに、どのプロジェクトの課題・状態か区別できるようにする
- **課題を立てるときも同じ基準を適用する**。値が一つに決まり、代替案が無い修正は、課題に残さずその場で直す。課題として残すのは、判断や選び方が要るものだけ

### 作り方

- 開閉は `details` / `summary` で行う。JS を使わずに畳める
- 状態バッジの色は 未＝灰・着手＝橙・済＝緑。既存のバッジ色に合わせる
- **既定の開閉は状態で決める**。未・着手は `<details open>`、済は `open` なし
- **`details` はそのままでは Markdown に落ちない**。**`md-flat` を付けると見出しに展開される**（クラスは「クラス名」を参照）。付けない `details` はタグのまま出て畳める

## 指示された範囲だけを実装する

- **いま作業しているプロジェクトに関するルールだけを変更対象にする**。
  ほかのプロジェクトのルールは、触らない
- **範囲外のずれを見つけたら、指摘する**。**見つけた応答の中で言う。作業が一区切りつくまで持ち越さない**
- **追加・変更を指示されたら、指示された項目だけを実装する**。関連して良くなりそうな項目を勝手に足さない
- 既存の記述を移動・削除するのも変更にあたる。重複の解消などで必要と判断したら、実装前に提示して確認を取る
- **勝手に直してよいのは、文字コード・改行コードの違反と、検討の余地がない修正**（値が一つに決まり、代替案が無いもの。例: `.gitignore` に既定の除外パターンを1行足す、実態と合わなくなった文言を削る）。**判断や選び方が要るものは、直す前に報告する**

## 名前を変えたら全体を検査する

適用条件: ファイル・実行ファイル・コマンドの名前を変えるとき、置き場を移すとき。

- **`text find` で全体を探す**（`--path . --recurse`）。**`--recurse` を忘れると root 直下しか見ない**
- **Grep では足りない**。cmd は SJIS、reg は UTF-16 で、どちらも Grep から漏れる
- **古い名前と新しい名前の両方を見る**。消した名前が残っていないか、新しい名前が正しい場所に入ったか
- **テストが通っても検査を省かない**。名前が別のものを指したままでもテストは通る

## 複数の解決案がある場合の対応

- **問題に対して、解決できる可能性が高い対処案が2つ以上ある場合、実装する前にそれぞれの案を提示する**
- ユーザーに選んでもらってから実装に進める。独断で1つを選んで進めてはいけない
- **推奨する案を A にする**。以降 B・C と、推す順に並べる
- **なぜ推すかを 1 行添える**
- **決める点が複数あるときは番号を振る**。`1-A` `2-B` の形にし、部分的に採否を伝えられるようにする
- **恒久対策と暫定対策を分けて書く**。案ごとにどちらかを明示する。**同じ事象が再発するなら暫定である**
- **暫定だけを並べない**。恒久対策が無いなら、無いと書く
- **解決しない案を選択肢に混ぜない**。「何もしない」「一部だけ直す」は案ではなく、放置と部分実行である

## 複雑な案を出す前に、簡単な代替が無いか調べる

適用条件: 実装量が多い案・undocumented な手法・リスクのある手法を提案するとき。

- **一般的な知識だけで最初に思いついた方法を、検索せずに提案しない**。まず簡単な代替が無いか検索してから提案する
- **理由**: 広く知られている手法が唯一の方法とは限らない。調べれば実装量・必要権限・壊れやすさの小さい代替が見つかることがある（実例: プロセスのコマンドライン取得で PEB を自前でたどる方法を提案したが、検索したら `NtQueryInformationProcess` の専用の問い合わせ種別で1回の呼び出しで済む方法があった）

## ファイルの移動・分割・置き換え時の順序

- **コンテンツを新しい保存先に書き込んでから、元の場所の記述を削除する**（削除→作成の順にしない）
- 理由: 利用制限やAIエージェントが応答不可など、途中で処理が中断する可能性は常にある。削除を先に行うと、作成前に中断した場合にデータが失われる

## 並列で読ませるとき

適用条件: ワークフロー・サブエージェントで手分けして読むとき。

- **落ちた分を黙って捨てない**。上限・エラーで通らなかった本数を数え、報告に書く
- **通った分だけで「全部見た」と読める書き方をしない**
- **件数の上限を先に決める**。上限に当たったら本数を減らして残りを回す

## 質問された時の対応

- **ユーザーの発言が質問なら、まず回答だけを返す**。修正・追加・削除などの作業を先に進めない
- **不具合・問題点についての質問なら、直ちに全ての作業を止めて誠実に回答する**
- **回答後、対処方法・修正方針をユーザーに提示し、確認を得てから実行に移る**
- 「〜は可能？」「〜できる？」も質問。実装してよいかは別途確認する

## 未検証の技術的挙動を、確認済みであるかのように断定しない

適用条件: Windows API・ランタイム（Node/Bun 等）の挙動など、実機で確かめられることを説明するとき。

- **コメント・記憶・一般論からの推測を、実測したかのように言い切らない。** 「〜のはず」「未確認だが」等、検証していないことが分かる書き方にするか、断定する前に実測する
- **理由**: 個別の検証ツール（Markdown が GitHub で崩れていないかを確かめる `check-markdown`、HTML の色が読めるかを実機で計測する `check-contrast` 等）ではすでに「推測で判断しない」が徹底されているプロジェクトでも、口頭の技術的主張はその徹底から漏れやすい。実例: 「Node はコンソール出力コードページを自動で書き換える」という未検証の前提から「別のツールと動きが不揃いになる」と指摘し、あとで実測により誤りと判明した

## ルールの記述規則

- ルールには適用条件を明記する。理由は、判断に迷うケースの助けになる場合のみ残し、自明な理由や経緯は書かない
- 新しいルールを追記する際は、既存内容と重複していないか確認し、同じ内容は1箇所にまとめる
- 参考CSSなど再現に必要な具体的な値（色コード等）は圧縮・言い換えの対象にしない
- ルールを変更した後は、既存の生成済みファイルに矛盾が生じないか確認する
- ルール修正案の出し方は「複数の解決案がある場合の対応」に従う
- **モデル名をルールや指示に書かない**。役目の大きさで書く
- **文末は短くする**。できるだけ体言止めを使う。

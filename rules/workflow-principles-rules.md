# 進め方の原則

## 修正は1点ずつ、確認を重視

- **1回の実装は1点の修正のみ**
- **`git add`・`git commit` は自動でしない**。ステージングも含め、「commitして」と指示されるまで待つ
- **`git mv` ・ `git rm` はステージングを伴うが、ファイルの移動・削除の手段として使ってよい**。ただし `git add -N` は使わない
- **Edit・Write と `git commit` を、同じ応答に並べない**。Edit の失敗を見る前に commit が走り、壊れたファイルが入る。フックは、同じ応答の中の失敗を知れない。結果を見てから、次の応答で commit する
- **commit を指示されたら、載せるファイルを名指しして `git add <path>…` し、commit も `git commit -m … -- <path>…` で同じファイルを名指しする**。`git add -A` ・ `git add .` ・ `git commit -a` は使わない (フックで止まる)
- **commit にもパスを書く**。`git mv` ・ `issue set` などが先に stage したものは、パスを書かない commit に混ざる
- **載せるのは、その指示の対象として自分が変えたファイルだけ**。commit の前に `git diff --cached --name-only` で一覧を見る
- **一括で載せると、別のセッションや人が書き換えたファイルまで入る**
- **`git reset` は使ってよい。ただし実行する前に、何がどうなるかを説明して確認を取る**
  - 説明すること: 実行するコマンド、戻るコミット・ステージ、作業中の変更が残るか消えるか
  - **`--hard` は作業中の変更を戻せない形で消す**。説明にそう書く
  - 確認の取り方は「重大な操作の確認方法」に従う
- **指示は1回きり有効** - 「commitして」は、そのとき目の前にある変更にだけ及ぶ。以降の作業で再びコミットするには、改めて指示が要る
- **ビルド確認は行う** - エラーの有無は確認するが、機能確認はユーザに任せる
- **自動実行（タスクスケジューラ・cron・フック等）に関わる変更は、実環境から動かして結果を見るまで「済」にしない**。手元での手動実行は、実行ユーザ・環境変数・PATH・カレントが違うため、代わりにならない
- **終了コード0や「完了」の表示を、成功の証拠にしない**。成果物（生成されたファイル・ログの終了行）で確かめる
- **テストがあるプロジェクトでは、全件実行してから報告する**（実行時期は「いつ実行するか」）
- **複数の修正が必要な場合** - 1つ実装後「完了。次のステップは？」と確認待ちする

**理由**: ユーザが各修正を確認・検証できないと、問題発生時の原因特定が困難。コミット前に確認できることで、修正の妥当性をユーザが判断できる

## 利用者に見せる前に、自分で見る

適用条件: 画面・資料・出力を利用者に見せて、見た目の承認や動きの確認を頼むとき。

- **頼む前に、利用者と同じ形で動かし、画面を撮って自分の目で見る**。明暗・開く場所・選ぶものを、利用者の使い方に近づける
- **撮るのは、確かめる窓だけにする**。画面の範囲 (`CopyFromScreen` 等) を撮らず、撮る窓から写す。撮った絵を見る前に、写っているのが確かめる窓だけかを確かめる。画面の範囲を撮ると、ほかの窓 (個人の情報) が写り、会話の記録に残る
- **見ただけで分かる不具合を、利用者に見つけさせない**。見つけたら直してから頼む
- **試験の合格を、見た代わりにしない**。中身の値を読む試験は、画面に描かれたかを確かめない
- 「修正は1点ずつ、確認を重視」の「機能確認はユーザに任せる」は、この確認を省いてよいという意味ではない

## 機能を追加・変更するときの順序

適用条件: 新しい機能を足すとき、既存の動きを変えるとき。

- **計画（`notes/10_plan/`）→ ユーザの承認 → status に着手を反映 → 実装 → status と計画に結果を反映**、の順で進める
- **決めることを聞くのが先。作業は後**。利用者がいるときは、決めることを先に全部、1 つずつ選択肢で聞き、答えを全部もらってから作業 (計画を書く・調べる・作る) に入る。作業の途中で、決めることを聞くために止めない
- **計画の承認は、計画書を書く前にもらう**。計画の中身 (何をどの順で作るか・決めたこと) を先に示し、決めることと一緒に承認をもらう。計画書は、その後に決まったとおりに書く。順は「決めることと承認を全部聞く → 計画を書いて開く → 実装する」
- **理由**: 作業してから聞くと、その間ずっと利用者が待つことになる
- **実装してから計画に書く順序にしない**。書く段階で気づく設計の穴を、作り終えてから見つけることになる
- **ファイルを置き換える計画には、古いファイルの削除を手順に入れる**
- **計画の冒頭に、何を読み、どこへ書くか (対象のプロジェクト ・ 入力 ・ 出力) を 1 行で書く**。取り違えを、承認の前に見つける
- 実装中に計画と違う判断をしたら、その場で報告する。黙って計画から外れない
- **大きな変更は別の計画書を立てて実装する。ただし全体像は詳細仕様に置き、実装後に必ず最新へ更新する** (「仕様の書き方と置き場」)。計画書は書き換えない。詳細は個別の計画書に置き、全体像からリンクで参照する
- **全体像が古いと、読み手はどれが正か判断できない**。実装したものが正である

### 前からある動きを無くさない

適用条件: 既存の機能・部品を直す・置き換えるとき。

1. **直す前に、その部分に今ある動きを書き出す**。直す関数・部品が受け持つ動き (表示・音・tooltip・色・キー・メニュー) を、コードと詳細仕様から拾う。書く場所は、課題 (計画があれば計画) の「今ある動き:」で始まる段落。どの試験で守るかを 1 つずつ添える。書き出せない部分は、直す前に試験で確かめて今の動きを見る
2. **書き出した動きのうち、試験が無いものは、直す前に試験を足す**。今の動きで ✅ になることを確かめ、直した後も同じ試験で見る
3. **描画・受け口を置き換えるときは、置き換える前に出していたものを全部、置き換えた後も出しているかを見て確かめる**。直した点だけでなく、同じ操作で出ていた他の表示も見る
4. **デグレが見つかったら、まず原因を調べて、利用者に詳しく説明する**。どの commit・版で無くなったか (前の版で 1 つずつ戻して特定する)、なぜ試験が捕まえなかったか、同じ形を防ぐ試験とルールを書く。直す前に、無くなったことを再現する試験で ❌Red を見る
5. **動きを変える commit の前に、載せる課題か計画に「今ある動き:」があるかを見る**。無ければ commit せずに書き足す。資料だけ・試験だけ・体裁だけの commit は除く

**理由**: 新しい機能のために別の機能が無くなるのは重大な事故。手順 1 だけでは書き出しが飛ばされた

### 実装のあとに何をするか

適用条件: 作業がひと区切りついたとき、commit した・していないと報告するとき、次の作業を決める・尋ねられるとき。

- **この 3 つの報告の終わりには、尋ねられなくても次の作業を 1 件だけ提案する**。ひと区切りついたとき、commit していないと報告するとき、commit したと報告するとき
- **記録（status・計画書・issues）の反映が済んでいなければ、それを最優先の次の作業にする**。運用作業（待受けの張り直し等）や別の課題への着手を先に提案しない
- **「次は?」「で」「残」「残作業は?」等、直前の作業の続きを問う短い発言も同じ扱いにする**。まず直前の作業に関連する残作業の有無を確認し、記録の反映が未了ならそれを真っ先に挙げる
- **関連する残作業が無ければ、その旨を伝えたうえで、ほかに残作業（記録・課題・状態）が無いか確認する**
- **候補を挙げるときは、優先度が最も高いものから 1 件だけに絞る**。選択肢が要る場面でも複数並べない

## 課題の管理

適用条件: これから解決することを記録するとき。

- **課題は `notes/40_issues/` に置き、グループ（章）で束ねる**。`issue` に移したプロジェクトは 1 件 1 ファイルで、`issue` で読み書きする。置き場・README からの案内は TOOLS-USAGE の「課題を管理する (issue)」に従う
- **移す前のプロジェクトは、`issues.html` の 1 ファイルに全件を書く**。1 件が長くなってきたら 1 件 1 ファイルへ切り替える（`i260830-13-件名.html`）
- **番号は `i` ＋ `yymmdd-nn`**（`i260830-13`）。`i` は issue、以降は立てた日と **36 進数 2 桁**の連番（英字は小文字。`l` は大文字の `L` と書く。「ファイル名」の `nn` を参照）。id も表示も同じ形にする
- **課題の調査・対応計画は `r` `p` ではなく issue の `i` 番号を流用する**。`notes/01_research/i260830-13-件名.html`、`notes/10_plan/i260830-13-件名.html` のように、置き場は種別のフォルダのまま番号だけ issue のものを使う
- **状態は 未 / 着手 / 済 の 3 段階**。課題の中の「やること」も同じ 3 段階で持つ
- **片付いた課題は消さずに済で残す**。グループごと片付いたら保管へ移す (`issue archive <グループ>` で `archived/` へ)。移すときに本文を書き換えない
- **移す前のプロジェクトは、保管先を `issues-archive.html` にする**。`issues.html` は未が 0 件でも残し、README からは `issues.html` だけにリンクする
- **status には課題を書かない**。status は「いまどうなっているか」、issues は「これから何をするか」
- **実装が済んでいるものを記録に追いつかせるのは、確認を取らずに行う**。issues のやること・状態、status の進捗、グループの件数と目次。**書き換えるのは記録だけで、実装は変わらない**
- **件数と状態は中身から数え直す**。手で書いた値がずれていたら、その場で直す
- **「まだ済んでいないものを済にする」のは別**。済かどうかを実測してから書き換える
- **`issue migrate` で移す前に、課題の状態が正しいかを確かめる**。済んだのに未・着手のまま、済んでいないのに済、を直してから移す。移した後は、古い状態がそのまま正として残る
- **他プロジェクトからの報告に基づく課題は、実装・テストが済んでも、報告元の確認が取れるまで「済」にしない。** 実装した旨を報告元へ返信し、検証を依頼する。報告元から OK が出た時点で「済」にする
  - **完了の報告には、依頼元の確認が無いと課題を閉じられないことと、確かめたら返信してほしいことを書く**。何を確かめればよいか (流すコマンド・見るファイル) も添える。書かないと、依頼元は読んで終わり、返信が来ない
- **課題の一覧・status のタイトル（`<title>`・タイトルバー内 `h1`）にはプロジェクト名を含める**。複数プロジェクトを横断して見るときに、どのプロジェクトの課題・状態か区別できるようにする
- **課題を立てるときも同じ基準を適用する**。値が一つに決まり、代替案が無い修正は、課題に残さずその場で直す。課題として残すのは、判断や選び方が要るものだけ
- **課題を立てる前に、済と保管を含む既存課題の全件を、試験の名前・関数の名前・事象の語で探す** (移したプロジェクトは `issue search`)。同じ事象の既存課題があれば新しく立てず、既存課題に足す

### 作り方

適用条件: `issue` に移す前のプロジェクトで、`issues.html` を手で書くとき。

- 開閉は `details` / `summary` で行う。JS を使わずに畳める
- 状態バッジの色は 未＝灰・着手＝橙・済＝緑。既存のバッジ色に合わせる
- **既定の開閉は状態で決める**。未・着手は `<details open>`、済は `open` なし
- **`details` はそのままでは Markdown に落ちない**。**`md-flat` を付けると見出しに展開される**（クラスは「クラス名」を参照）。付けない `details` はタグのまま出て畳める

## 指示された範囲だけを実装する

- **いま作業しているプロジェクトに関するルールだけを変更対象にする**。
  ほかのプロジェクトのルールは、触らない
- **範囲外のずれを見つけたら、指摘する**。**見つけた応答の中で言う。作業が一区切りつくまで持ち越さない**
- **追加・変更を指示されたら、指示された項目だけを実装する**。関連して良くなりそうな項目を勝手に足さない
- 既存の記述を移動・削除するのも変更にあたる。重複の解消などで必要と判断したら、実装前に提示して確認を取る
- **勝手に直してよいのは、文字コード・改行コードの違反と、検討の余地がない修正**（値が一つに決まり、代替案が無いもの。例: `.gitignore` に既定の除外パターンを1行足す、実態と合わなくなった文言を削る）。**ルールに書いてあるのに資料に無いもの（作業漏れ）も同じ。確認を取らずにルールどおりに直し、何をどこへ足したかを報告する**。**判断や選び方が要るものは、直す前に報告する**

## 名前を変えたら全体を検査する

適用条件: ファイル・実行ファイル・コマンドの名前を変えるとき、置き場を移すとき。

- **`text find` で全体を探す**（`--path . --recurse`）。**`--recurse` を忘れると root 直下しか見ない**
- **古い名前と新しい名前の両方を見る**。消した名前が残っていないか、新しい名前が正しい場所に入ったか
- **テストが通っても検査を省かない**。名前が別のものを指したままでもテストは通る

## 複数の解決案がある場合の対応

- **問題に対して、解決できる可能性が高い対処案が2つ以上ある場合、実装する前にそれぞれの案を提示する**
- ユーザに選んでもらってから実装に進める。独断で1つを選んで進めてはいけない
- **推奨する案を A にする**。以降 B・C と、推す順に並べる
- **なぜ推すかを 1 行添える**
- **決める点が複数あるときは番号を振る**。`1-A` `2-B` の形にし、部分的に採否を伝えられるようにする
- **複数の案件を同時に進めているときは、案件をまたいで通し番号にする**。件ごとに 1 から振り直さない（`1-A` が二度出ると、どちらを指すか分からない）
- **`issue decide migrate` が済んだプロジェクトでは、番号を `issue choice next` で取る**。セッションや worktree をまたいでも重ならない。それ以外のプロジェクトでは、会話の中の最大に 1 を足す
- **恒久対策と暫定対策を分けて書く**。案ごとにどちらかを明示する。**同じ事象が再発するなら暫定である**
- **暫定だけを並べない**。恒久対策が無いなら、無いと書く
- **解決しない案を選択肢に混ぜない**。「何もしない」「一部だけ直す」は案ではなく、放置と部分実行である

## 複雑な案を出す前に、簡単な代替が無いか調べる

適用条件: 実装量が多い案・undocumented な手法・リスクのある手法を提案するとき。

- **一般的な知識だけで最初に思いついた方法を、検索せずに提案しない**。まず簡単な代替が無いか検索してから提案する
- **理由**: 広く知られている手法が唯一の方法とは限らない。調べれば実装量・必要権限・壊れやすさの小さい代替が見つかることがある（実例: プロセスのコマンドライン取得で PEB を自前でたどる方法を提案したが、検索したら `NtQueryInformationProcess` の専用の問い合わせ種別で1回の呼び出しで済む方法があった）

## ファイルの移動・分割・置き換え時の順序

- **コンテンツを新しい保存先に書き込んでから、元の場所の記述を削除する**（削除→作成の順にしない）
- 理由: 利用制限やAIエージェントが応答不可など、途中で処理が中断する可能性は常にある。削除を先に行うと、作成前に中断した場合にデータが失われる

## 並列で読ませるとき

適用条件: ワークフロー・サブエージェントで手分けして読むとき。

- **落ちた分を黙って捨てない**。上限・エラーで通らなかった本数を数え、報告に書く
- **通った分だけで「全部見た」と読める書き方をしない**
- **件数の上限を先に決める**。上限に当たったら本数を減らして残りを回す
- **検索・フェッチだけを行うサブエージェントは、役目の小さいモデルで立てる**。起動時にモデルを指定する。指定しないと親と同じ大きいモデルで動く

## 質問された時の対応

- **ユーザの発言が質問なら、まず回答だけを返す**。修正・追加・削除などの作業を先に進めない
- **不具合・問題点についての質問なら、直ちに全ての作業を止めて誠実に回答する**
- **回答後、対処方法・修正方針をユーザに提示し、確認を得てから実行に移る**
- 「〜は可能？」「〜できる？」も質問。実装してよいかは別途確認する

## 未検証の技術的挙動を、確認済みであるかのように断定しない

適用条件: Windows API・ランタイム（Node/Bun 等）の挙動など、実機で確かめられることを説明するとき。commit したか・ファイルを書いたか・記録に反映したか・コマンドが動いたか、を報告するときも同じ。断られた・失敗したコマンドも、何が動いたかを確かめてから言う。

- **コメント・記憶・一般論からの推測を、実測したかのように言い切らない。** 「〜のはず」「未確認だが」等、検証していないことが分かる書き方にするか、断定する前に実測する
- **「直した」「足した」と報告するときは、変えたファイルと行を添える**。`git diff` か Grep で、入ったことを見た所を書く。添えられないなら、直していない
- **原因を書くときは、同じ文に根拠 (コードの場所・測った値) を添える**。添えられないときは「見込み (確かめていない)」と書く
- **理由**: 個別の検証ツール（Markdown が GitHub で崩れていないかを確かめる `check-markdown`、HTML の色が読めるかを実機で計測する `check-contrast` 等）ではすでに「推測で判断しない」が徹底されているプロジェクトでも、口頭の技術的主張はその徹底から漏れやすい。実例: 「Node はコンソール出力コードページを自動で書き換える」という未検証の前提から「別のツールと動きが不揃いになる」と指摘し、あとで実測により誤りと判明した

## ルールの記述規則

- ルールには適用条件を明記する。理由は、判断に迷うケースの助けになる場合のみ残し、自明な理由や経緯は書かない
- **ルールを追記・変更するときは、既存の記述と重複していないかを確かめる**。移す・分けるときも同じ
- **照らし合わせるのは共通ルールの全章**。同じ章の中だけを見ない（`rules/` の Grep で、要の語を探す）
- **重なっていたら 1 箇所に寄せ、もう片方は消す**。参照が要るときだけ、見出し名で指す
- 参考CSSなど再現に必要な具体的な値（色コード等）は圧縮・言い換えの対象にしない

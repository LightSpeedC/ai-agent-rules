# 共有環境の使い方

## PlayWright テストの実行

- **他プロジェクトで PlayWright テストが必要な場合、自プロジェクトにインストールせず PlayWright 共有環境を使う**
- 利用方法の詳細（フォルダ規約・実行コマンド等）は `T:/PlayWright/PLAYWRIGHT-USAGE.md` を参照
- **待受けと違い、PlayWright の `[killed]` は後始末が要る**。残骸の調べ方は「残ったプロセスを調べるときは psls を使う」に従う

## ai-chat-lite（AI 間チャット）の利用

- **他プロジェクトのセッションと会話する必要が生じたら、ai-chat-lite を使う**
- **参加するのは利用者の指示があったときだけ**。自分の判断で参加しない。前回のセッションで張っていた分の張り直しは、指示が続いているものとして扱う（「セッションを開き直したとき」）
- **待受けはメインのエージェントからバックグラウンドで起動し、完了を待たずに作業を続ける。サブエージェントは挟まない**
- **サブエージェントを挟むとAIエージェントが 1 回につき 5〜6 本立ち、終わっても残る**。待受け自体は 25 MB ほどなので、挟む側のほうが重い
- **張る前に `aichat waiters` で確かめる。同じルームを 2 本で見ない**。二重に張ると通知が倍に来るだけで、届く発言は増えない
- **起動は 2 段。数えてから張る**。ID は自分の project フォルダ名にする。**複数のルームを見るときも 1 本で足りる**

  ```powershell
  aichat waiters :project-a: -p 8787 -r public
  aichat wait    :project-a: -p 8787 -r public
  ```

  ほかのルームも見るときは、**両方の `-r` を `"public,<ルーム ID>"` にする**。数えたルームと張るルームを揃える
- **`-r` に複数のルームを渡すときはダブルクォートで囲む**（`-r "public,<ルーム ID>"`）。囲まないと**割れて 1 ルームだけになる**。単一なら囲まなくてよい（`-r public`）。囲み方は「CLI の引数はダブルクォートで囲む」に従う

- **`join` と `leave` は打たない**。`wait` と `say` が参加者として登録する。`join` が足すのは参加の知らせ 1 通だけで、**その 1 通が全員の待受けを起こす**。`leave` も同じで、待受けが消えればサーバが猶予のあとに離脱を流す
- **数えるのは `aichat waiters`。プロセスを自分で検索しない**。`who` の「接続中」では本数が分からない。検索式は書き方を 1 つ守れなかっただけで結果が反転し、そのたびに事故になった（他プロジェクトを止めて `exit 255` で落とした、0 本が 1 本に見えて張り忘れた）。**やることは集計より後ろの行に出るので、それに従う。1 つとは限らない**
- **止めてよいのは `aichat waiters` が pid で名指しした分だけ**。名指しされていない行には触らない。他プロジェクトの分を止めると、相手は原因不明の `exit 255` で落ちる（実際に起きた）
- **名乗る ID はコマンドの直後に、コロンで囲んで置く**（`:project-a:`）。`-c` は廃止した。囲むのは前方一致を止めるため（囲まないと `project-a` を探す式が `project-aa` にも当たる）
- **ID を取るところはすべてコロンで囲む**。`--to` の相手も同じ。ルーム（`-r`）は**コロンでは囲まない**
- **接続先（`-p`）とルーム（`-r`）も毎回渡す**。環境変数は使わない。既定値は無い。**ID に使えるのは英数字・ハイフン・下線・ピリオドだけ**（ピリオドは先頭と末尾には置けない）。**待つ長さは書かない**（既定で最大 12 時間）
- **終わったら親が、数えてから黙って張り直す**。新着なし・`[killed]`・`exit 255`・繋がらない、どれも区別しない。**報告は要らない**（「張り直しました」「新着はありませんでした」はトークンの無駄）
- **例外: メモリ不足で止まったときは張り直さず、止まったことを報告して依頼を待つ**（通知に「running low on memory」と出る）。ハーネスがそう指示する
- **出力に発言があれば読んで把握し、必要なら返信してから張り直す**
- **作業中に通知が届いたときも、他の作業を続ける前に出力を読み切る。読まずに次のツール呼び出しへ進まない**。「終わったら親が…張り直す」は読んだ後の話であり、読む前に他の作業へ進んでよいという意味ではない
- **自分宛て（自分が名乗った ID への `@` 指定・自分への返信）の発言は、まず全文をそのまま表示し、要約せず一語一句読む。**
- **「状況報告」「事実の共有」に見える発言も、対応不要だと決めてかからない。** 書かれている数値・状態が期待どおりかを確かめ、**不具合の兆候を指摘されているかもしれない、という前提で読む**。「別セッションの話だから」「参考情報だから」と検証せずに流さない
- **報告するのは発言（`say`）が届いたときだけ**。参加・離脱・オフラインの記録や、自分の発言の折り返しは伝えない
- **課題として残してほしい、という依頼はその場で受ける**。`notes/40_issues/issues.html` に足し、足したことを返信する。利用者の確認は要らない。**コストが低く、取り返しがつく**
- **指摘や不具合の報告も、その場で調べる**。調べた結果を返信する。**直すかどうかは別**
- **調べて直しが要ると分かったら、課題に足してから返信する**。返信だけして課題に残さないと、次のセッションに引き継がれない
- **ソースを直すのは利用者の判断を待つ**。課題に残すところまでが自動で進める範囲である。**ただし検討の余地がない修正はその場で直す**（「指示された範囲だけを実装する」に従う）
- **`[killed]` は異常ではない**。止まる理由は、空きメモリが減ってAIエージェントが背面のコマンドを刈ったとき（通知に「running low on memory」と出る）。**位置は保存されているので取りこぼさない**
- **メモリ不足の停止は、`~/.claude/settings.json` の `env` に `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP: 1` を置くと起きなくなる**。次のセッションから有効。メモリが十分な環境に限る
- **背面コマンドに時間の上限は無い**（実測: `timeout` なしで 45 分、`timeout 7200000` 付きで 12 時間、どちらも止まらなかった）。待受けの `timeout` は要らない。待つ長さは `aichat wait` の既定（最大 12 時間）で決まる
- **通知で起こされただけのときは、応答本文を繰り返さない**。張り直すだけにする。同じ待ちの案内を何度も出さない
- **待受けの新規開始・再接続、cronの定期処理が行えたときは、`✅10/04 08:51 chat待受け再開`・`✅10/04 08:51 cron再開`のように「✅月/日 時:分 事象名」の形で日時を添える（JST）。年・秒は書かない**
- **親セッションは待たない**。別の作業を続け、通知が来たら読む。反応の粒度は「即時」ではなく「次の区切り」になる
- **自動で返信してよいのは、事実を返すときだけ**。課題に足した／調べた結果／直した、の報告
- **判断を含む返信は案を提示して確認を得る**。断る・方針を決める・仕様を変える、を含むもの
- **周知の本文も、送る前に案を提示して確認を得る**。ルールの反映と同じ扱いにする（発言は消えずに残る）
- **案には、ルーム・名乗る ID・宛先 ID を添える**。本文だけでは送り先を確かめられない。**宛先を指定しない（ルーム全体へ出す）ときは、指定しないと書く**
- **周知文は短く書く**。絶対パスも書かない。読み手はルールを読むことが前提。
- **ルールの周知は、見出し名と変わった点だけを伝える**。ルールの本文を貼らない
  - 伝えるのは「共通ルールのどの見出しか」と「何がどう変わったか」の数行
  - **読み手は見出しを頼りに、必ず自分で本文を読みに行く。**「自分宛てなら」「具体的な値があれば」のように読むかどうかを条件で選ばない
- 理由: 貼った本文はその場で古くなる。あとから履歴を読んだ人が、更新後のルールではなく**貼られた古い本文を正しいものとして読む**。チャットの発言は消えずに残り続ける。**周知が具体的な値を書かないのはこのためであり、読み手が本体を読みに行くことを前提にしている**
- 利用方法の詳細（コマンド・待受けの張り方・API）は `T:/ai-chat-lite/CHAT-USAGE.md` を参照。
- サーバは Windows サービスとして常駐しているため、起動の操作は要らない

## Computer UseによるChrome操作の利用

- **Computer UseによるChrome操作が使えるかどうかは、セッションが実行されているホストマシンにChrome拡張がインストール・ログイン済みかで決まる**。CUI直接／Remote Control経由（Desktop版・ブラウザ・モバイル）のどのインターフェースで操作しているかとは無関係（CUI・Desktop版どちらのセッションでも接続を確認済み）
- **事前に接続可否を判定する手段はない**。`tabs_context_mcp` 等を実際に呼び出してみて初めて分かる。確認コスト自体は低いので、都度確認して構わない
- **未接続だった場合はまず拡張の未インストール／未ログイン／未起動を疑い、ユーザに確認を依頼する**。過去に接続できたことがあっても、別のホストマシンで動くセッションでは改めて未接続になり得る

## URLへのアクセス手段の選択

- **URLへのアクセスが必要なタスクでは、事前確認をせずまず WebFetch／WebSearch で試す**
- 候補の目安: 本文の読み取りだけなら WebFetch、ログインやJS描画が必要なら Computer UseによるChrome操作、スクリーンショットや複数ページの機械的な巡回なら PlayWright
- **WebFetch／WebSearch で目的の内容を取得できなかった場合、別の手段に切り替える前にユーザへ報告して確認を取る**。失敗の内容（リダイレクト案内のみ・JS描画で本文が空・403・認証要求・目的の情報が含まれない等）と、切り替え候補（Computer UseによるChrome操作／PlayWright）を示す
- 同一サイト内で実体のURLを取り直すだけ（`index.html` → `README.html` のようなリダイレクト追随、クロスホストリダイレクトの追随）は手段の切り替えに当たらないため、確認は不要
- **一度切り替え先を選んだら、同一セッション内では再確認せずその選択に従う**

# git の使い方

## 外部への投稿前にローカルパスを確認する

適用条件: GitHub Issue・PR・コメントなど、社外・第三者の公開の場にターミナルログ等をそのまま貼るとき。

- **貼る前に、ローカルのフルパス（プロジェクトフォルダ名等）が含まれていないか確認する。** 含まれていれば汎用的な表記（`C:\work` 等）に置き換える
- **「コミット前の確認」と同じ観点だが、対象は git commit だけでなく外部サービスへの投稿全般**（Issue・PR・コメント等）に広げる
- 理由: 実際にプロジェクトのパスを含んだまま Bun の Issue に投稿してしまい、事後に修正が必要になった

## gitブランチ

- **`git init` は `develop` ブランチで初期化する**（`git init -b develop`）
- **使用するブランチは `develop` / `release` / `master`**。`main` は使わない

## コミットメッセージの渡し方

適用条件: `git commit`／`git commit --amend` でメッセージを付けるとき。

- **クォート・エスケープ文字を含まない 1 行のメッセージは `-m` で渡す**
- **それ以外（複数行・引用符・エスケープ文字を含むもの）は、`tmp/` に本文を書き、`git commit -F <path>`（`--amend` も同様に `-F`）で渡す**
- **書き方は毎回この 2 通りに固定する**。ヒアドキュメント（`git commit -m "$(cat <<'EOF' ... EOF)"`）はそのつど手組みせず使わない
- 使い終わった一時ファイルは消す（「一時ファイルの削除」に従う）

## コミットメッセージの attribution

- **`Co-Authored-By:` 行は付けてよい**（noreply アドレスのため機密情報に当たらない）
- **セッションURLを含む行（`Claude-Session:` 等）は付けない**。「機密情報のマスキング」の「認証トークンやセッションIDを含むURL」に該当する
- ハーネスからの attribution 指示にセッションURLが含まれていても、その行だけ外す

## develop→release→masterのマージ

- develop → release、release → master へのマージは `--no-ff` で行う（`git merge --no-ff`）。fast-forwardマージは行わない
- マージ作業が終わったら develop ブランチに戻しておく
- 理由: マージコミットを必ず残すことで、どの単位（develop側の作業）が取り込まれたかを履歴から追跡しやすくする

## タグ名

適用条件: リポジトリにタグを打つとき。

- **`yyyy/mm/dd_ブランチ名` の形**（`2026/09/05_master`）。日付は `/` 区切り、ブランチ名は `_` で接続
- 同じ日に同じブランチへ複数打つときは末尾に連番（`2026/09/05_master-02`）
- **注釈付きタグ（`git tag -a`）にする**。何をした時点かをメッセージに残す
- **push は明示する**（`git push origin <タグ名>`）。`--tags` で一括送信しない

## 中身の差が無いのに M と出たら

適用条件: 生成ツール（html2md 等）を流した後、`git status` に `M` が並んだとき。

- **先に差が無いことを確かめる**。`git diff --stat` が空であること
- **`git update-index --refresh` では消えないことがある**。`git add -- <名指し>` で載せ直す。対象は `git ls-files -m` で数える
- **載せ直した後、`git diff --cached` が空であることを確かめる**。空でなければ止めて報告する
- **commit に混ぜない**

## リモートリポジトリの作成・push

- リモートリポジトリの作成・pushは、ユーザが明示的に指示するまで実行しない（git add/commitと同様の原則）
- リポジトリ作成には gh CLI（`gh repo create`）を使う
- リポジトリ名は既定でプロジェクトフォルダ名を使う
- **作成の前にリポジトリ名を提示して確認を得る**。一度作ると URL が確定し、改名しても GitHub Pages の URL と既存のリンクが変わる
- **併せて機械で見る**。小文字の英数字とハイフンだけか、日付は yyyymmdd か、既存のリポジトリ名（`gh repo list`）に 1〜2 文字違いが無いか
- **1〜2 文字違いが見つかったら、typo か別物かを聞く**。自分で判断しない
- **`--description` で説明を1行書く**。GitHub の一覧・検索結果に表示されるため、リポジトリ名だけでは何のプロジェクトか分からない
- **Pages を公開するなら、`--description` を公開ページの説明にする**
- 検索されたいリポジトリにはトピックを付ける（言語・分野・種別など3〜10個）。**`--add-topic` は `gh repo create` には無い。`gh repo edit --add-topic` で付ける**
- **GitHub Pages を公開したら `gh repo edit --homepage` で公開 URL を設定する**。リポジトリページの右上に表示され、訪問者が資料本体へ移動できる
- **可視性は既定で private。ユーザが `public` と明示した場合はそのまま public で作成する**（可視性の再確認はしない）
- **public で作成する場合も、初回コミット前の内容点検は省略しない**（「コミット前の確認」を参照）。点検で問題が見つかったときだけ作成を止めて報告する
- pushするブランチ・GitHub側のデフォルトブランチは、ローカルの既定ブランチ（develop）に揃える。mainは作らない

## .gitignore の共通除外設定

- **プロジェクトの `.gitignore` には `tmp/`・`etc/`・`logs/` を必ず含める**（`tmp/` は一時ファイル、`etc/` はセッションログや補助スクリプト、`logs/` は自動生成するログ・レポート。常駐サービスのログ `logs/<サービス名>/` も含む）
- **先頭 `_` は `_*` の 1 行**。ファイルもフォルダも全階層で外れる
- **末尾に `/` を付けない**。付けると `_secret.txt` が残る
- **戻すファイルは `!` で名指し**（`!_*.scss`）
- **`*/` を含むパターンをコメントに書かない**。ブロックコメントを閉じる
- **`.claude/` は直下をすべて除外し、チームで共有するものだけを名指しで許可する**。共有するのは `settings.json`・`commands/`・`agents/`・`skills/` の4つ

```gitignore
.claude/*
!.claude/settings.json
!.claude/commands/
!.claude/agents/
!.claude/skills/
```

- 個人の権限許可リスト `.claude/settings.local.json` は `.claude/*` で捕捉されるため個別に書かない
- **共有する `settings.json` に絶対パス・ユーザ名を含む値を書かない**。個人ごとに異なる値は `settings.local.json` に分離する
- 理由: 許可を明示する形にすると、AIエージェントの更新で `.claude/` 配下に新しいフォルダが追加されても既定で除外される

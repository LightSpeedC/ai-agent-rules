## 運用

### 1. chat 待受け・共通ルールの追随の点検

このプロジェクトは public ルームを常時見る。手順は共通ルールの「ai-chat-lite（AI 間チャット）の利用」に従い、ここには**値と頻度だけ**を書く。

2026-09-22 以降、`common-rules.md` が共通ルールの実体になった（ホーム配下は `@` 参照のみ）。2026-09-24 に全19章を `rules/` へ切り出したため、実体は `common-rules.md` と `rules/` 配下に分かれている。他プロジェクトのセッションも直接これらのファイルを編集しうるため、**git 管理外の変更（未commitの差分）を見つけたら履歴に残す**。

#### 値

| 項目 | 値 | 備考 |
|---|---|---|
| ID | `:ai-agent-rules:` | project フォルダ名。コロンで囲む |
| 接続先 | `-p 8787` | 本番 |
| ルーム | `-r public` | 1 本だけ見る。単一なのでクォートは要らない |
| 点検の頻度 | `5 6-22/2,0 * * *` | 6 時〜24 時の間、2 時間おき、毎時 5 分 |
| 追随の対象 | `common-rules.md`・`rules/` | root の1ファイルと、切り出し先の全ファイル |
| 文字コード | `--to utf8/lf` | BOM 無し UTF-8 ＋ LF。`convert-encoding` で揃える |

#### 引き金

- **6 時〜24 時の間、2 時間おきの定期点検**（毎時 5 分、cron）
- **ルール変更の通知を受けたとき**。ai-chat-lite で共通ルールの変更を知らされたら、共通ルールの追随は次の定期点検を待たずにその場で行う
- **セッションを開き直したとき**。待受け・cron はどちらも前セッションの分が切れているため、両方を張り直す

#### やること

- **chat 待受け**: `aichat waiters` で本数を確かめる。自分の分が 0 本なら `aichat wait` で張り直す。他プロジェクトの分には触らない
- **cron**: `CronList` で残っているか確かめる。無ければ `CronCreate` で登録し直す（頻度は上の表の「点検の頻度」、prompt は「ローカルルール「chat 待受け・共通ルールの追随の点検」に従って点検する。」）
- **待受けが完了したら、間に他の作業を挟まず即座に張り直す**。完了から張り直しまでの間は誰も listen していない空白になり、その間に投稿された発言は catch-up されず取りこぼす（実例: 2026-09-22、空白の約12秒に挟まった発言を取りこぼした）
- **定期点検のたびに `aichat recent -n 30` で直近を突き合わせ、取りこぼしが無いか確かめる**。新着として拾えていない発言が見つかったら、通常の新着と同様に本文を示して対応する
- **新着発言（join / leave / オフラインの記録を除く）は、要約せず本文をそのまま応答に示す**
- **共通ルールの追随**: `git status --short common-rules.md rules/` で未commitの変更を確認する。差が無ければ何もしない。報告もしない
- **差分が通知内容と一致するか確かめるときは、対応する発言の `#` 番号を応答に書く**（例:「#998の内容と一致」）
- **文字コード違反（BOM・改行等）があれば、変更が見つかったファイルに `convert-encoding <path> --to utf8/lf` で直す**
- **公開チェックを通す**。共通ルールの「コミット前の確認」に従う。1 件でも残れば commit せず報告する
- **`common-rules.md` と `rules/` 配下の変更ファイルだけを stage して commit し、続けて push する**。ほかのファイルは含めない
- **commit・push したら、ルール変更の通知本文は全文、コミット内容は diff 形式で応答に示す**

#### 決めごと

- **待受けは常に 1 本張る**。他プロジェクトの分には触らない
- **cron の指示文に手順を書かない**。共通ルールの見出し名で参照する

#### 共通ルールと違うところ

共通ルールの「修正は1点ずつ、確認を重視」は **commit を自動で行わない**、「重大な操作の確認方法」は **push を別指示が要る操作**と決めている。ここはそれと違い、**確認を取らずに commit し、続けて push する**。

- **なぜ**: 原本は別のセッションからも書き換わる。取りこぼすと、どの版で何が変わったかが履歴から読めなくなる。全19章が `rules/` へ切り出し済みのため、書き換わるのは `common-rules.md` 側だけではない。commit だけで push しないと、他プロジェクトのセッションが見るのはリモート（GitHub）側になるため、ローカルに留めたままでは追随が伝わらない
- **どこまで**: `common-rules.md` と `rules/` 配下だけ。ほかのファイルは stage しない
- **いつまで**: 暫定運用のあいだ。終えるときにこの章ごと捨てる

### 2. Codex への共通ルール配布

Codex は `@path` の取り込み記法を持たない。代わりに `@path` の直後へ日本語コメントで指示を書き、Codex 自身に読みに行かせる形にした。

- **パスは `W:`（subst）ではなく `C:\work` を直接使う**。Codex では `W:` の subst が正しく解決できなかった
- **1 ファイルのときの書き方**（下記コード例）
- **分割したときの書き方**: `@path` の直後に「◯◯の場合は `C:\work\...\xx-rules.md` を読む。」という日本語コメントを添える

```markdown
以下のルールを読んで。
@C:/work/ai-agent-rules/common-rules.md
<!-- 作業開始前に `C:/work/ai-agent-rules/common-rules.md` を読み、現在の作業に適用される指示に従うこと。読み込めなかった場合は、その旨を報告すること。 -->
```

### 3. 章の切り出しルール

`common-rules.md` の大見出し（`#`）1 章を `rules/` へ切り出すとき、**両側に同じ見出しを残す**。

- **`common-rules.md` 側**: 見出し（`#`）を残し、本文を `@rules/xxx-rules.md` 参照＋Codex 用コメントの1ブロックに置き換える
- **切り出し先（`rules/xxx-rules.md`）側**: 同じ見出しをファイル先頭に置く

```markdown
# 見出し名

@rules/xxx-rules.md
<!-- ◯◯を作成・編集するときは `rules/xxx-rules.md` を読み、その指示に従うこと。 -->
```

**なぜ**: 見出しを消すと、`common-rules.md` を読んだときにその章が存在すること自体が分からなくなる。両側に残すことで、どちらを読んでも章の所在が分かる。

### 4. Claude フックの置き場とメンテ

`~/.claude/settings.json` の hooks（SessionStart・Stop）が呼ぶフックの実体を、このプロジェクトに置く。コピーはしない。詳細は `tools/80_ops/claude-hooks/README.html` に書いてある。

#### 値

| 項目 | 値 | 備考 |
|---|---|---|
| 置き場 | `tools/80_ops/claude-hooks/` | ts の 2 本（`copy-session-jsonl.ts`・`load-obsidian-memory.ts`） |
| 呼び方 | `node "W:/ai-agent-rules/tools/80_ops/claude-hooks/<名前>.ts"` | `settings.json` の hooks のコマンド。`W:` が見えない環境では動かない |
| テスト | `tools/40_test/run-tests.cmd` | node と bun の全件 |
| Vault の場所 | 環境変数 `AI_AGENT_OBSIDIAN_VAULT` | 未設定なら何も注入しない |

#### やること

- **フックを変えるときは、テストを先に書き、全件を通す**。通したあと、`settings.json` のコマンドそのままで試走する
- **別の PC では、`settings.json` の hooks を、その PC のこのリポジトリの置き場に向けて書く**

#### 落とし穴

- **再開（`--continue` / `--resume`）では、`additionalContext` が会話にある分と同じだと、同じ回の `systemMessage` ごと捨てられる**（Claude Code の重複排除）。表示を出すフックは、毎回違う短い `additionalContext` を一緒に渡す
- **`settings.json` を書き換えても、動いているセッションには効かない**。次の起動・再開から有効になる

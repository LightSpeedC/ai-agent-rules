2026-11-19 に file-manager から報告 (#2057、fm-w3 で発生)。guard-commit-after-failed-edit.ts が、存在しないパスへの Edit の失敗を印にすると、そのパスには Read も Edit も通せず (ファイルが無い)、印が解けない。以降、そのセッションの commit が全部止まる。向こうの直し案: 存在しないパスの失敗は数えない。または、解く手段を別に用意する。関連: i261114-02 (worktree の外のパスの失敗) は、cwd の外だけを数えない直しで済んだ。今回は cwd の中の、存在しないパス。やること: (1) 再現する試験を先に書き、❌Red を見る (2) 直し方を決める (3) 直す。今ある動き: 失敗したままの Edit・Write の後の commit を止める (i261101-01)、cwd の外の失敗は数えない (i261114-02)。守る試験は tests/ のこのフックの試験。

**やること**

- [済] 再現する試験を先に書き、❌Red を見る (存在しないパス 3 件の ❌Red、フォルダ・`..` の 2 件の ❌Red を確認)
- [済] 直し方: A (利用者の決定、2026-11-19)。フックが動く時点でディスクに無いパス・フォルダを指すパスの失敗は数えない。理由の文言は見ない。cwd の外は有無を調べない (guard-commit-after-failed-edit.ts の failedFiles)
- [済] 実装・試験 (node 332 件通過、bun は当該ファイル 27 件通過)・README・settings.json のコマンドでの試走
- [未] 報告元 (file-manager) の確認。確かめ方: 存在しないパスへ Edit を失敗させたあと、同じセッションで git commit が止まらないこと。確かめたら、この課題へ返信してほしい (確認が取れるまで「済」にしない)
- [未] 残りの穴の扱い (下の「レビューで残した穴」)

**設計・コードレビューの対応 (2026-11-19、サブエージェント。rules-review の子セッションが無かったため)**

- 取り入れた: exists を引数にして試験で差し替えられる形にする・cwd の外は有無を調べない・フォルダは数えない (`isFile`、強く疑えた 1 件を ❌Red で確かめて直した)・`..` を畳む (`normalize`)
- レビューで残した穴 (今回は直さない。起きうる条件を記録): ① シンボリックリンク・8.3 の短い名前・subst (`W:` と `C:/work`) の表記ゆれで、失敗と解く操作のキーが別になる。② Edit も Read も権限で拒否されるファイルの失敗は解けない (permissions.deny 等が前提で稀)。③ 巨大ファイル・バイナリの Read が上限で失敗する場合の扱いは未確認。④ フックの deny の結果が `is_error` で記録されなければ、1 回止めたあと次の commit で印が消える (推測、未実測)。⑤ `git.exe commit`・`& git commit`・`bash -c` は isCommit に当たらず止めない (抜け道)。⑥ 「同じ失敗で N 回止めたら通す」出口は、利用者の判断が要るため、足していない (どの穴にも当たらない出口になるが、守りが弱くなる)
- 既知の限界: 存在しないパスへの Edit が打ち間違いだと、本来の編集が未適用のまま commit に進める (壊れたファイルは載らないので、このフックの目的の外)

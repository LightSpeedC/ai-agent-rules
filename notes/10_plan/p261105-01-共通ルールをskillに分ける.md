# p261105-01 共通ルールを skill に分けて常時読み込みを減らす

共通ルール (`common-rules.md` と `rules/`、約 198 KB、約 7.5 万トークン) の状況別の章を skill に移し、常時読み込む分を核だけにする。入力: `rules/` の全ファイル。出力: `skills/` の `SKILL.md` 群と、ホームの skill の置き場へのシンボリックリンク、変更後の `common-rules.md`。

## 2. 核と skill の切り分け (案)

## 3. 手順

1. **試験: 1 章だけ (sqlite) で、仕組みを確かめる。**
    - `skills/light-sqlite/SKILL.md` を作る (先頭に name と description、本文は `rules/sqlite-rules.md` を写す。**この時点では元を消さない**)。
    - ホームの skill の置き場に、実体の `C:` のパスへのシンボリックリンクを張る。**シンボリックリンクの作成に権限が要るかは未確認。要るなら、本人が実行するコマンドを案内する。**
    - セッションを開き直し、skill の一覧に出るか、SQLite の作業で本文が読み込まれるかを、実環境で見る。**結果を見るまで、次へ進まない** (共通ルールの「自動実行に関わる変更は、実環境で動かして結果を見るまで済にしない」)。
2. <strong>移行: 試験が通ったら、skill にする章を 1 つずつ移す。</strong>本文を `skills/<名前>/SKILL.md` に書いてから、`rules/` 側の本文を消す (書き込んでから削除する順)。移すたびに、`common-rules.md` の該当章を「見出し + skill の読み先 1 行 + Codex 用のコメント」に書き換える。
3. <strong>shell・coding は、核と skill に分ける。</strong>章の単位で分け、文は書き換えない (指示された範囲だけ実装する)。
4. <strong>再測: /context の Memory files を測り直す。</strong>約 7.5 万から約 2.7 万になったかを、前後の数字で計画書に書く。Skills の欄が増えた分も書く。
5. <strong>共通ルールの周知。</strong>共通ルールの変更に当たるので、変更の見出しと変わった点だけを、public ルームへ周知する (案を出して確認を得る)。
6. <strong>追随の仕組みを直す。</strong>ローカルルール 1 の「追随の対象」に `skills/` を足す。ローカルルール 3 (章の切り出しルール) を、skill の形に書き直す。
7. <strong>記録。</strong>status に着手・結果を反映し、詳細仕様 (`notes/50_spec/`) に、核と skill の一覧と読み込みの仕組みを書く。

## 4. 未確認とリスク

- <strong>skill が、確実に読み込まれるとは限らない。</strong>説明文が曖昧だと、必要な章が読み込まれない。破られると困る決まりを核に残したのは、そのため。試験で、説明文の書き方を決める。
- <strong>ホームの skill の置き場への、シンボリックリンクが効くかは未確認。</strong>効かなければ、実体を置き場へ写し、リポジトリ側を正とする同期の手順を足す案に変える (その場合は、改めて案を出して確認を得る)。
- <strong>他プロジェクトのセッションに、skill が見えるかは未確認。</strong>ホームの置き場なので見えるはずだが、試験で別のプロジェクトから確かめる。
- <strong>クラウド (`../ai-agent-rules/`) では、ホームの skill の置き場が無い。</strong>クラウド向けの置き場とリンクの張り方は、別の計画にする。この計画の範囲に入れない。
- <strong>Codex は、skill の仕組みを調べていない。</strong>18-B のとおり、`common-rules.md` のコメントから `skills/…/SKILL.md` を読ませる。
- <strong>同じ文を 2 か所に置かない。</strong>移す章は、移した後に `rules/` 側の本文を消す。

## 1. 解きたいこと

「ルールの抽象化と配布単位」（`p260904-01`）は**エージェント軸**（Claude Code／Codex／Gemini CLI 等）で固有度を分けた。今回はもう 1 つの軸である**OS 軸**（Windows／Mac／Linux）を重ね、どこから分割・分岐・分家させるかの順序を決める。

Mac・Linux での運用が控えている以上、**Windows 専用の記述を残したまま渡すと、他 OS のセッションには意味をなさない記述が混ざる**。エージェント軸と同じ問題が、OS 軸でも起きる。

さらに、閉域網でのローカル LLM 運用（Claude Code 自体の向き先をローカルモデルへ変更する場合を含み、Aider・OpenClaw 等の別ハーネスも制限しない）を見据えると、**到達できる外部・LAN 資源の違い**という第 3 の軸も要る。ローカル LLM を使うこと自体は既存の**エージェント軸**の延長（対応機能の差）で扱えるが、**インターネットや特定の LAN サービスに到達できるか**は独立した軸になる。

## 2. 三軸で見る（OS × Agent × 接続性）

OS 軸・Agent 軸に加え、**接続性軸**（インターネット到達要 ／ LAN内サービス到達要 ／ 何にも依存しない）を重ねる。3 つの軸すべてに依存しない部分が、最も安全に・最初に切り離せる。

| 象限 | 内容 | 代表例 | 分割の優先度 |
|---|---|---|---|
| ✅ **OS非依存 × Agent非依存** | 成果物の作り方・言語仕様・外部サービスの話。**実は同じ集合**（下記参照） | HTMLデザインルール・HTML→Markdown変換・GitHub Pages・SQLite・テスト・git/GitHub系一式 | ✅ **最優先** |
| ⚠ **OS依存 × Agent非依存** | どのエージェントでも Windows で動かす限り必要になる記述 | PowerShell／cmd／bat／ps1／psh／CP932 関連（シェル実行ルール大半） | ⚠ **2 番目** （Mac/Linux 版を別に作る） |
| ⚠ **OS非依存 × Agent依存** | Claude Code の機能に依存するが、OS には依存しない | ai-chat-lite の利用・ファイル出力/公開・claude-in-chrome・セッションログ自動保存・Obsidianメモリ連携 | ⚠ **2 番目** （`p260904-01` の agents/ と同じ扱い） |
| **OS依存 × Agent依存** | 両方に依存する記述 | 該当なし（実測では見つからなかった） | — |

> [!IMPORTANT]
> **「OS非依存 × Agent非依存」の集合は、`p260904-01` で既に洗い出した「固有語ゼロ」の集合とほぼ一致する**。HTMLデザインルール・HTML→Markdown変換・学習資料・テストのルール・SQLiteの大原則・HTMLログ・ドキュメント日付、そして`git` 本体に関するワークフロールール項目（gitブランチ・attribution・マージ・タグ名・コミット前の確認・.gitignore の共通除外設定）は、**エージェントの機能にも Windows の仕組みにも触れていない**。二重に安全な塊であり、最初に切り離す根拠が 2 つ重なる。
> **`git` 本体と GitHub は分けて扱う**。`git`・`git push` はリモートが LAN 内の社内サーバーでも動く（閉域網でも使える）が、`gh` CLI・`api.github.com`・GitHub Pages は github.com への到達が必須で、**閉域網では使えない**。「リモートリポジトリの作成・push」（`gh repo create` 前提）・「外部への投稿前にローカルパスを確認する」（GitHub Issue/PR 前提）・GitHub Pages 公開ルール一式は、GitHub 固有として接続性軸の「インターネット到達要」に入る。

### 接続性軸を重ねる

共通ルールは、到達できる資源によって 3 段階に分かれる。

| 段階 | 依存先 | 代表例 |
|---|---|---|
| ❌ **インターネット到達要** | github.com・api.github.com 等の外部サービス | GitHub Pages 公開ルール一式・リモートリポジトリの作成・push（`gh` CLI 使用）・外部への投稿前にローカルパスを確認する（GitHub Issue/PR 前提）・`check-markdown`（`api.github.com`）・WebSearch/WebFetch・claude-in-chrome |
| ⚠ **LAN内サービス到達要** | 特定の場所（家・会社）で常駐する社内サービス・共有ドライブ | ai-chat-lite（`-p 8787` のサービス常駐前提）・PlayWright共有環境・ai-agent-tools共有環境（`N:/` subst経由） |
| ✅ **何にも依存しない** | ローカルの成果物・言語仕様だけ | 「両方非依存」の集合（上表）がそのまま該当 |

「両方非依存」の集合は接続性軸でも最上段（何にも依存しない）に該当し、**3 軸すべてで非依存**という最も安全な塊であることが確認できる。

> [!NOTE]
> **`git` 本体（ブランチ運用・commit・マージ・タグ・push）は表のどこにも固定されない**。ローカル操作（commit・ブランチ切替）は「何にも依存しない」だが、`push` はリモートの到達先次第で「LAN内サービス到達要」（社内 git サーバー）にも「インターネット到達要」（github.com へ push）にもなる。**意図・手順は 3 段階どこでも共通**で、変わるのは push 先の値だけなので、値の差し替えで済む shared 扱いにする。

## 3. 両方非依存（最優先で切り離せる）

実測（2026-09-22、行数 1,501・128,839 文字）で、次の章がこの集合に入る。

| 章 / 項目 | OS依存の語 | Agent依存の語 |
|---|---:|---:|
| HTMLデザインルール（全章） | 0 | 0 |
| HTML→Markdown 変換ルール | 0 | 0 |
| GitHub Pages 公開ルール | 0 | 0 |
| 学習資料の作成ルール | 0 | 0 |
| テストのルール | 0 | 0 |
| SQLite の大原則 | 0 | 0 |
| HTML でログを出力する | 0 | 0 |
| ドキュメントの作成日・更新日 | 0 | 0 |
| インデント／文字コード変換は1回だけ／全角半角桁揃え／アプリログ日時形式（コーディングルール内） | 0 | 0 |
| `git` 本体 5 項目（gitブランチ・attribution・マージ・タグ名・コミット前の確認） | 0 | 0 |
| .gitignore の共通除外設定 | 0 | 0<sup>*</sup> |
| 課題の管理・複数の解決案がある場合の対応・質問された時の対応・複雑な案を出す前に調べる 等（進め方の原則） | 0 | 0 |

<sup>*</sup> `.gitignore の共通除外設定`は設定フォルダ名（`.claude/`）だけが agent 依存。値の差し替えで済み、`p260904-01` の shared 扱いのまま変わらない。

> [!WARNING]
> **GitHub固有（`gh` CLI・`api.github.com`・GitHub Pages）はこの表に含めない**。OS・Agent軸には依存しないが、接続性軸で「インターネット到達要」に入るため、3軸すべて非依存ではない。GitHub Pages公開ルール・リモートリポジトリの作成/push（`gh`部分）・外部への投稿前にローカルパスを確認する・`check-markdown` がこれに該当する。
> **「リモートリポジトリの作成・push」の見出しは、分岐前に `git push`（本体側）と `gh repo create`（GitHub側）へ分ける必要がある**。現状は1見出しに両方が混在しており、そのままでは片方だけを切り出せない。

> [!NOTE]
> **git・GitHub 系は3つ目の推し**。`git`・`gh` はどの OS でもコマンド名・引数が同じで、ブランチ運用や attribution の意図もエージェントを問わない。`p260904-01` では「gitブランチ」「develop→release→masterのマージ」等を個別項目として common に分類していたが、**OS 軸を重ねても崩れない**ことが今回で確認できた。

## 4. OS依存（Windows専用）の実態

「シェル実行ルール」章が最も密度が高い。24 見出しのうち、Windows の仕組み（PowerShell／cmd／bat／ps1／psh／タスクスケジューラ／Defender／CP932）に直接触れるものが約 13、OS を問わない原則が約 6、値だけ差し替えれば済むものが約 5。

| 区分 | 項目（抜粋） |
|---|---|
| ❌ **Windows専用** | PowerShellツールが無いときはpshで呼ぶ／実行ファイル名に.exeを付けない／cmdの( )の中は!で読む／昇格・タスクスケジューラから動かすとき／PowerShellの実行ポリシー／PowerShellの落とし穴／残ったプロセスの調べ方（psls・taskkill）／カレントの実行ファイルは明示パスで実行する／ブロックされたら回避しない（Defender前提）／bat・cmd・ps1の文字コード規定／SetConsoleOutputCP／標準出力をUTF-8に揃える（CP932前提）／Bun同士のパイプが文字化けする（Windowsコンソール前提） |
| ✅ **OS非依存** | エラーが出たらそこで止める／検索・集計の結果が0件なら検索式を疑う／対象を渡すコマンドは渡ったことを確かめる／同期APIは非同期処理を止める／プロセスの識別性／bun・nodeでFFIを使うとき（概念部分） |
| ⚠ **値の差し替え** | コマンド実行の優先順位（PowerShellツール／Bashツールの呼び名）／パスの区切り（cmd/batの例外部分のみ）／CLIの引数はダブルクォートで囲む（cmdのシングルクォート挙動のみ）／一時ファイルの保存先（scratchpadのパス表記のみ） |

Mac・Linux 版を作るときは、**この章を丸ごと持ち出すのではなく、OS非依存の原則（上表中段）だけを残し、Windows専用の項目は `agents-or-os/windows/` のような置き場に移す**。Mac・Linux 側は同じ構造（コマンド実行の優先順位・エラー処理の原則等）に、bash／zsh／シェルスクリプトの実例を差し替えて別途書く。

### 前提とするツールの有無・版

軸そのものではなく、**分岐後の各ファイルの「適用条件」に明記すべき前提**。OS軸・Agent軸のどちらとも別に、実行環境ごとに次の差がある。

| ツール | 有無 | 版の幅 | 関わるルール |
|---|---|---|---|
| `node` | ✅ **全環境にある前提** | v22.2 系・v20.8 系など、環境によって違う | 「移植で落ちるのは、言語が肩代わりしていた比較」等、node の版差に触れるものは版を明示する |
| `bun` | ⚠ **無い環境がある** | あれば v1.4.0 系・v1.4.2 系 | 「bun と node で FFI を使うとき」「Bun 同士のパイプは文字化けする」。**bun が無い前提のフォールバックを常に書く** |
| `git` | ✅ **全環境にある** | それなりに版差がある | `git` 本体のワークフロールール項目。新しいサブコマンド・オプションの有無に注意 |

**「無い環境がある」と「版がまちまち」は別の扱いになる**。前者はルール側に分岐（フォールバック）が要り、後者は断定を避けて「版によって異なる」と書くか、確認手順（`--version` 等）を添える。

## 5. 決めること

| # | 決めること | 選択肢 | 推す案 |
|---:|---|---|---|
| 1 | 分割の順序 | 3軸すべて非依存の集合を先に切る ／ 軸を1つだけ選んで先に切る | **3軸すべて非依存の集合を先に切る**。1回の作業で3つの軸の対象から同時に外れ、以後どの計画（`p260904-01`／本計画）でも「済」として扱える |
| 2 | 置き場所の構造 | `p260904-01` の `common/・shared/・agents/` に `os/` を追加する ／ 別のディレクトリ階層を新設する | **追加する**。`agents/claude-code/` と並べて `os/windows/` を置けば、既存の分類方式のまま拡張できる |
| 3 | この計画の実施タイミング | 暫定運用（`common-rules.md` 1ファイル）が続く間は分割しない ／ 先に本計画の分類だけ済ませておく | **分割しない**。`p260910-01` の「暫定を終える条件」がまだ揃っておらず、分類の検討（本計画）と実際のファイル分割は別工程として扱う |

### この計画で扱わないこと

- **実際のファイル分割・生成処理**。「ルールの分割と配布」で扱う
- **Mac・Linux 側の具体的な文面（bash/zsh の実例等）**。実際に Mac・Linux での運用が始まってから書く
- **4 象限のうち「OS依存 × Agent依存」の探索**。実測で 0 件だったため、見つかった時点で扱う
- **接続性軸の「LAN内サービス到達要」を、さらに場所（家・会社）で細分するか**。現時点では場所の違いは接続性軸に帰着すると見て、独立した軸にはしない

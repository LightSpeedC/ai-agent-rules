# r261105-01 ルールのサイズを減らす調査

共通ルール (`common-rules.md` と `rules/`) が大きく、AI エージェントのコンテキストを圧迫している。減らし方をネットで調べ、案を出す。入力: 実測したファイルの大きさ、会話の記録の使用トークン、Web 上の資料と Claude Code の公式資料。出力: この調査。

## 1. 現状の実測 (2026-11-05)

- 合計 約 198 KB (`common-rules.md` 6.2 KB と `rules/` の 28 ファイル)。
- 大きい順: html 21.6 KB ・ shell 21.5 KB ・ workflow-principles 17.3 KB ・ coding 16.4 KB ・ project-layout 13.9 KB ・ shared-env 11.3 KB ・ workflow-record 9.4 KB ・ markdown 9.3 KB ・ test 9.0 KB ・ workflow-confirm 8.4 KB。上位 10 ファイルで全体の約 7 割。
- 会話の記録の最初の応答の使用トークン: 新しく書き込んだ分 93,004 + キャッシュから読んだ分 36,018 = 約 129,000。これはシステムの指示・ツールの定義・共通ルール・Vault の目次などの合計で、共通ルールだけの量ではない。
- **/context の実測 (11/05、利用者が実行)**: 窓は 100 万トークン。使用は 17.6 万 (18%)。内訳は Memory files 7.5 万 (7.5%) ・ Messages 6.4 万 ・ System tools 2.8 万 ・ Skills 5,203 ・ System prompt 3,352 ・ MCP server instructions 1,002 ・ Custom agents 85。Memory files が、会話以外の固定分で最大。共通ルール 約 198 KB は、約 7.5 万トークンに当たる (1 トークンあたり約 2.6 バイト)。
- 必要なときだけ読み込まれる分 (deferred) は、MCP tools 40.2 万 ・ System tools 2.8 万で、窓の使用には入っていない。

## 2. 分かったこと (ネットの資料)

下の資料はブログなどの二次資料が中心。Claude Code の公式資料で確かめたのは、フックの種類だけ (次の章)。数値は経験則で、鵜呑みにしない。

| 事柄 | 内容 |
|---|---|
| 取り込みでは減らない | `@` で取り込んだファイルは起動時にすべて読み込まれる。章に分けても、読み込む量は減らない。減るのは、条件で読み込むものだけ |
| 条件付きの読み込み | `.claude/rules/` に置き、`paths:` を付けたものは、該当するファイルを触ったときだけ読み込まれる。`paths:` が無いと毎回読み込まれる。skill は必要になったときだけ本文が読み込まれる |
| 長さの目安 | 1 ファイル 200 行以下。毎回効く決まりだけを置き、手順や一部にだけ効く決まりは skill か `paths:` 付きに移す |
| 増えると守られない | 規則が増えると、見落としが先に増え、次に無視される。公式の上限は無く、「150 行」などは経験則。ベンチマーク (IFScale) では、よいモデルが 150 規則あたりまで高い遵守率を保つとされる |
| 止める手段 | 破られては困る決まりは、文でなくフックや CI で止める |
| Codex の上限 | Codex は `project_doc_max_bytes` の既定 32 KiB を超えると、続きを読み込まない。198 KB のままでは、Codex 側では途中から効かない (未実測) |
| 増え続ける | エージェントの設定ファイルは、規則が積み上がり続けるという研究がある (arXiv) |

## 3. フックの種類 (15-A の調査。公式資料)

課題 i261101-01 (失敗したままの Edit・Write の後の git commit を止める) の 15-A は、失敗を状態ファイルに書き、commit の前に読む案。そのためのフックの種類を、公式のフックの資料で確かめた。

| 事柄 | 分かったこと |
|---|---|
| 失敗を知らせるフック | `PostToolUseFailure` がある。ツールの呼び出しが失敗した後に走る。`PostToolUse` は成功したときだけ走り、失敗では走らない |
| 入力の項目 | 共通の項目に、`tool_name` ・ `tool_input` ・ `tool_use_id` が付く。`PostToolUseFailure` の項目の細部 (エラー本文の名前など) は、資料の該当箇所を読めておらず**未確認** |
| 並べた呼び出しの順 | 同じ応答で並べたツールの `PostToolUse` が、次のツールの `PreToolUse` より先に走るかは、資料に書かれていない (**未確認**)。同じ種類の事象に付くフックどうしは、並列で走る |
| まとまりの終わり | `PostToolBatch` がある。並べた呼び出しが全部終わった後、次にモデルを呼ぶ前に走る。終了コード 2 で、ループを止められる |

**実測 (11/05、仮の測定フックを 3 本登録し、セッションを開き直して測った。測り終えて外した)**:

- 成功した Edit は、`PreToolUse` と `PostToolUse` の両方が走った。
- <strong>old_string が合わずに失敗した Edit では、`PreToolUse` も `PostToolUseFailure` も走らなかった (2 回とも)。</strong>入力の検査の段階で失敗し、フックに届かないとみられる。**つまり、15-A の `PostToolUseFailure` では、この種類の失敗を拾えない。**
- 同じ応答で Edit と `git commit --dry-run` を並べたとき、commit の `PreToolUse` が走った時点の会話の記録には、<strong>同じ応答の Edit と commit の呼び出しは、まだ入っていなかった。3 秒待って読み直しても、入っていなかった (2 回目の測定)。</strong>入るのは、応答のまとまりが終わった後。
- したがって、commit の `PreToolUse` から同じ応答の失敗した Edit を知る手段は、いまのところ無い。`PostToolBatch` (並べた呼び出しがすべて終わった後) は、間に合わない (commit は済んでいる) が、事後の警告には使える見込み。未測定。

## 4. 案と、選んだもの

| 番号 | 案 | 種別 |
|---|---|---|
| 16-A | 常時読み込みを、毎回要る核 (セキュリティ・確認の語・進め方の原則・シェルの要点) に絞り、状況別の章は skill へ移す。各章の「適用条件」を、そのまま skill の説明文にできる | 恒久 |
| 16-B | 拡張子で決まる章 (html・sqlite・db-schema・markdown・tutorial 等) だけ、`paths:` 付きの rules にする。毎回効く章には使えず、16-A と併用する | 恒久 (部分的) |
| 16-C | 重複・経緯・例を削り、機械で止められるものはフックへ移す。規則はまた増えるので、単独では再発する | 暫定 |
| 16-D | 先に測る。起動時の読み込み量を測り、章ごとの大きさと並べて、どこを減らすかを決める。16-A の前の準備 | 準備 |

**選んだもの (11/05)**: 利用者は 15-A (i261101-01 の直し方。失敗を状態ファイルに書く) と 16-D (先に測る) を選んだ。16-A・16-B・16-C は、16-D の結果を見てから決める。

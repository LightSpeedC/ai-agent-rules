## 1. 実測の結果

### 発端

ps1 の先頭に `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8` を置いたスクリプトを cmd ランチャーから実行したところ、同じ窓で 2 回目以降に実行した SJIS の cmd の `echo` が化けた。新しい窓の 1 回目は化けない。引数なしの `chcp` は 932 と表示したまま、メッセージが英語（`Active code page`）になっていた。`chcp 932` を実行すると直った。

### 窓での検証（Windows 11 ・ 日本語表示 ・ cmd）

| 段 | 操作 | 実行後の窓（入力 / 出力） | 引数なしの chcp |
|---|---|---|---|
| 1 | 初期状態 | 932 / 932 | 日本語で 932 |
| 2 | C# の `Console.OutputEncoding = UTF8` | 932 / **65001** | 英語で 932 |
| 3 | `chcp 932` | 932 / 932 | 日本語で 932 |
| 4 | pwsh の `[Console]::OutputEncoding = UTF8` | 932 / **65001** | 英語で 932 |
| 5 | C# でリダイレクト時だけ `SetOut`（窓に直接出す） | 932 / 932 | 日本語で 932 |
| 6 | 同上をパイプ（`\| more`）に流す | 932 / 932 | 日本語で 932（`more` の表示は化ける） |

- **出力エンコーディングの設定は、プロセスが終わっても窓に残る**。C# も pwsh も同じ
- **変わるのは出力側だけ**。入力側は 932 のまま
- **引数なしの `chcp` は入力側を表示する**。出力側が 65001 でも 932 と出る。見分けられるのはメッセージの言語だけ
- **`chcp 932` は入力・出力の両方を戻す**
- 段 2 の直後、cmd の `echo`（SJIS）が化けた

### Bash から呼んだときの検証

| 実行のしかた | 日本語 |
|---|---|
| cmd の窓 ・ PowerShell から ps1 を実行 | 化けない |
| Bash から `pwsh -File` ・ `powershell -Command` を直接 | 化ける（CP932 で出る） |
| Bash から `psh` | 化けない |
| Bash から C# の exe（設定なし） | 化ける |
| Bash から C# の exe（`Console.OutputEncoding = UTF8`） | 化けない（ただし窓に残る） |
| Bash から C# の exe（リダイレクト時だけ `SetOut`） | 化けない（窓の出力は 932 のまま） |

SJIS の cmd も BOM 付き UTF-8 の ps1 も、ファイル自体は正しい。化けるのは受け手が UTF-8（Bash）のときだけ。

## 2. 外部の情報

### .NET SDK も同じ問題をバグとして直した

- .NET 7.0.3xx の SDK は、UI 言語が英語以外のとき CLI の出力のためにコンソールのエンコーディングを UTF-8 に変えるようにした（[CLI console output uses UTF-8](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/8.0/console-encoding)）
- その結果、`dotnet build` の後も窓が UTF-8 のまま残り、同じ窓で後から実行するプログラムに影響した。Microsoft はこれを「バグ」と明言している
- .NET 8 ・ .NET 7.0.300 SDK で修正され、終了後は窓のエンコーディングを変えない（[SDK no longer changes console encoding after completion](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/8.0/console-encoding-fix)）。戻し方の仕組みは書かれていない
- 推奨対処は「コードページを変えたいならアプリ自身が `chcp` を実行する。SDK に頼らない」

### PowerShell #25698（more へのパイプ）

- `echo 中文文本 | more` が化ける。PowerShell 7 の `$OutputEncoding` の既定が UTF-8 で、`more` は窓のコードページで読むため
- 提案は `$OutputEncoding = [Console]::OutputEncoding` を既定にすること。トリアージ待ちで、メンテナの回答はない（[PowerShell/PowerShell #25698](https://github.com/PowerShell/PowerShell/issues/25698)）

### Claude Code #81187

- PowerShell ツールで `chcp` を実行すると、以降の出力がセッションの終わりまで化ける
- 原因の説明は「コンソールのコードページは OS の共有かつ永続の状態で、後から起動する全プロセスが引き継ぐ」
- 提案は、ハーネスが毎回 `[Console]::OutputEncoding = UTF8` を設定すること。受け手が毎回揃える考え方（[anthropics/claude-code #81187](https://github.com/anthropics/claude-code/issues/81187)）

### 一般に紹介されている対処

- `[Console]::OutputEncoding` と `$OutputEncoding` の両方を UTF-8 にし、プロファイルに書く（[hy2k.dev](https://hy2k.dev/en/blog/2025/11-20-fix-powershell-mojibake-on-windows/)）。窓を常に UTF-8 にする割り切りで、SJIS の cmd とは相性が悪い
- リダイレクト時だけ `SetOut` で差し替える方法は、[System.Console](https://learn.microsoft.com/en-us/dotnet/fundamentals/runtime-libraries/system-console) の API の使い方としては載っているが、この文字化けの対処としてまとまった紹介は見つからなかった

## 3. 結論と方針案

| 論点 | 外部の情報 | 方針案 |
|---|---|---|
| 窓の設定が残るのは問題か | .NET SDK はバグとして修正 | 窓に触らない |
| 誰が揃えるか | 受け手が毎回揃える（#81187） | Bash からは psh 。C# はリダイレクト時だけ `SetOut` |
| cmd 系ツールへのパイプ | 窓のコードページで読むので化ける（#25698 ・ 未解決） | 受け入れる。UTF-8 の受け手を前提にする |

### C# の書き方

```csharp
if (Console.IsOutputRedirected)
	Console.SetOut(new StreamWriter(Console.OpenStandardOutput(), new UTF8Encoding(false)) { AutoFlush = true });
```

- `Main` の先頭に置く。これより前に書いた行は CP932 で出る
- 窓に直接出すときは何もしない。窓を誰も変えなければ化けない（段 5）。ほかのプロセスが途中で窓を変えると化ける（第 4 章）
- 受け手が cmd（`more` ・ `findstr` ・ `for /f`）だと化ける（段 6）

> [!NOTE]
> **finally で戻す形を採らない理由**: 強制終了すると戻らず、窓に残る。

## 4. 対処案の比較と追加検証

### 一時的に変えて、終了時に元の値へ戻す

ps1（5.1 ・ 7）でも C# でも同じ Win32 の出力コードページを変えるため、戻せば窓に残らない。戻すのは 932 ではなく、開始時に控えた値。

| 終わり方 | C#（finally のみ） | C#（finally ＋ CancelKeyPress） | ps1 5.1 ・ 7（finally） |
|---|---|---|---|
| 正常終了 ・ 例外 | 戻る | 戻る | 戻る |
| Ctrl+C | **戻らない**（実測） | 戻る（実測） | 戻る（実測。PowerShell が Ctrl+C でも finally を実行する） |
| 窓を閉じる | 戻らない。Win32 の `SetConsoleCtrlHandler` で捕まえられるが数秒で強制終了される（未検証） |  |  |
| `taskkill /F` | 捕まえられず、戻らない（未検証） |  |  |

- C# で `CancelKeyPress` から戻したとき、finally の表示は出なかった。ハンドラの後にプロセスが終わるため

### パイプでつないで同時に動かしたとき（実測）

「一時的に変えて元へ戻す」処理（C#）を `左 | 右` で同時に動かした。

| 段 | 動かし方 | 控えた元の値 | 最後の窓（出力） |
|---|---|---|---|
| 1 | 左: すぐ変えて 3 秒 ／ 右: 1 秒後に変えて 5 秒（左が先に終わる） | 左 932 ／ 右 65001 | **65001 のまま残る** |
| 2 | 左: すぐ変えて 5 秒 ／ 右: 1 秒後に変えて 1 秒（右が先に終わる） | 左 932 ／ 右 65001 | 932 に戻る |
| 3 | 窓に触らない pipe 方式どうし | — | 932 のまま |

- **後から始めた側は、先の側が変えた 65001 を「元の値」として控える**。後から始めた側が最後に終わると、窓は 65001 のまま残る
- どちらが先に終わるかは処理時間で決まり、書き手には制御できない。**パイプでつながれうる限り、元へ戻す方式では確実に戻せない**
- 窓に触らない方式（案 A）は、つないでも影響がない

### パイプされているかの検知

|  | 検知 | 書き出しを UTF-8 に差し替え |
|---|---|---|
| C# | `Console.IsOutputRedirected`（実測） | `Console.SetOut` で可（実測） |
| ps1 5.1 ・ 7 | `[Console]::IsOutputRedirected`（実測。Bash から呼ぶと True） | `[Console]::SetOut` で可。`Console.Out` だけでなく `Write-Output` ・ `Write-Host` も UTF-8 で出た（Bash から実測。窓での確認はまだ） |

- **後続が `more` か別の exe かは分からない**。分かるのはパイプかファイルにつながっていることだけ
- PowerShell の中の `.\a.ps1 | more` は、ps1 が出すのはオブジェクトで、`more` へ渡す文字コードは PowerShell の `$OutputEncoding` が決める

### パイプの左右が標準エラーを窓に出すとき（実測）

左が窓を 65001 に 3 秒変える（案 E）間、右は窓に触らずに標準エラーへ日本語を出し続けた。

| 段 | 右 | 左が 65001 にしている間 | 左が 932 に戻した後 |
|---|---|---|---|
| 1 | 窓に触らない C#（.NET Framework） | 化けない | **化ける** |
| 2 | SJIS の cmd の `echo`（for のブロック内） | **化ける** | **化けたまま** |
| 3 | 同上。左は窓に触らない pipe 方式 | 化けない |  |

- **.NET Framework の Console は、最初に書いた時点の出力コードページでエンコーダを決め、以後変えない**と考えられる。段 1 の右は 65001 の間に書き始めたため UTF-8 のバイト列を出し続け、窓が 932 に戻ると化けた。窓に直接出すときに Unicode で書くという当初の予想は誤り（.NET 7 以降は未検証）
- **cmd はバッチの行を、読んだ時点の窓のコードページで解釈する**と考えられる。段 2 は for のブロック全体を 65001 の間に 1 度で読んだため、SJIS の日本語が壊れたまま最後まで出た
- **窓を変える方式は、窓に触らない隣のプロセスまで壊す**。化けるかどうかは相手が書き始めた ・ 読んだタイミングで決まり、変えた側が戻しても直らない
- 窓に触らない方式（段 3）では、時間に関係なく化けない

### 標準入力 ・ 標準出力 ・ 標準エラーの 3 本（Bash から実測）

stdin に `入力あいう` を流し、stdout と stderr を両方 Bash で受けた。

|  | 差し替えない | リダイレクトされている分だけ差し替える |
|---|---|---|
| C# | 3 本とも化ける | 3 本とも化けない |
| ps1 5.1 | 3 本とも化ける | 3 本とも化けない |
| ps1 7 | 3 本とも化ける | 3 本とも化けない |

|  | 検知 | 差し替え（窓に触らない） | 窓ごと変える API（使わない） |
|---|---|---|---|
| 標準出力 | `IsOutputRedirected` | `SetOut` | `OutputEncoding` |
| 標準エラー | `IsErrorRedirected` | `SetError` | `OutputEncoding`（出力と共通） |
| 標準入力 | `IsInputRedirected` | `SetIn` | `InputEncoding` |

- **標準エラーは別に差し替える**。`SetOut` だけでは CP932 のままで、Bash の `2>&1` で化ける
- **標準入力は UTF-8 を受け取るときに差し替える**。差し替えないと `入力あいう` が `入力あぁE��` のように壊れて届いた
- `InputEncoding` は窓の入力コードページを変える。窓に残り、引数なしの `chcp` にはこちらが表示されるはず（未検証）
- 差し替えた後も、窓の入力 ・ 出力は 932 のまま

```csharp
var utf8 = new UTF8Encoding(false);
if (Console.IsOutputRedirected) Console.SetOut(new StreamWriter(Console.OpenStandardOutput(), utf8) { AutoFlush = true });
if (Console.IsErrorRedirected)  Console.SetError(new StreamWriter(Console.OpenStandardError(), utf8) { AutoFlush = true });
if (Console.IsInputRedirected)  Console.SetIn(new StreamReader(Console.OpenStandardInput(), utf8));
```

ps1（5.1 ・ 7）も同じ API で書ける（`[Console]::SetOut` 等）。

### 受け手を less ・ psh にしたとき（実測）

ai-agent-tools の `less`（node で動く）と `psh`（bun を優先し、無ければ node で動く）を試した。

| 入力 | less の表示（Bash ・ 窓とも） |
|---|---|
| CP932 で出す C# | 化けない（SJIS と判定して UTF-8 に直す） |
| UTF-8 で出す C# | 化けない |
| SJIS のファイル | 化けない |
| psh の出力 | 化けない |
| CP932 と UTF-8 が混ざったもの | 少ない側の行が化ける（全体を 1 つの文字コードと判定するため） |

- **Bash で `less` と打つと Git 付属の GNU less（`/usr/bin/less`）が動く**。ai-agent-tools の less はパスを明示する。cmd ・ PowerShell では `less.cmd` が先に見つかる
- 窓で less を使うと、画面を書き換えるため、前後の表示が消えることがある

### bun は動いている間だけ窓を 65001 にする（実測）

| 段 | 窓（入力 / 出力） |
|---|---|
| 初期状態 | 932 / 932 |
| bun の中から実行した子 | **65001 / 65001** |
| bun の終了後 | 932 / 932 |
| node の中から実行した子 | 932 / 932 |
| node の終了後 | 932 / 932 |

- **bun は入力 ・ 出力の両方を変え、終了時に戻す**。案 E と同じ動きで、パイプで同時に動く ・ 強制終了で窓に 65001 が残りうる。隣の SJIS の cmd ・ .NET Framework の exe が化けうる（bun を使った組み合わせでの確認はまだ）
- **node は窓に触らない**
- psh のソースは窓に触らない。psh 経由の PowerShell が 65001 を見るのは、ランチャーが bun を優先するため
- less は node で動くので窓に触らない

| 案 | 解決するか | 窓への副作用 |
|---|---|---|
| less（node） | する | ない |
| psh（bun で動く場合） | する | **ある** |
| psh（node で動く場合） | するはず（CP932 の行も読み分けるため。未検証） | ないはず |

### 常に chcp 65001 を前提にしたとき

| 対象 | どうなるか |
|---|---|
| SJIS の bat ・ cmd | `echo` の日本語が化ける。全部 UTF-8 に書き換える必要がある |
| 普通の C#（.NET） | 窓のコードページに合わせて UTF-8 で出すため、化けないはず（未検証） |
| 普通の ps1（7） | 表示は化けない。ネイティブへのパイプも既定が UTF-8 で揃う（未検証） |
| 普通の ps1（5.1） | 表示は化けない。**ネイティブへのパイプは `$OutputEncoding` の既定が ASCII で `?` になる**。これは 65001 でなくても起きる（Bash から `'日本語' \| findstr .` で実測。7 では化けない） |
| CP932 で書き出す古い exe | 化ける |
| `more` ・ `findstr` 等 | 窓が 65001 なら揃う。古い Windows では 65001 の `more` に不具合があったという話もある（未検証） |

### 対処案の一覧

| 案 | 内容 | 評価 |
|---|---|---|
| A | 窓に触らず、受け手が揃える。ps1 は psh で呼ぶ、または C# と同じくリダイレクト時だけ `SetOut` | 副作用がない。cmd 系の受け手では化ける |
| B | 環境変数があるときだけ UTF-8 で出す（`PYTHONIOENCODING` ・ `DOTNET_CLI_FORCE_UTF8_ENCODING` と同じ考え方） | cmd の受け手でも化けない。呼ぶ側が毎回指定する |
| C | Windows 全体を UTF-8 にする（ベータ: Unicode UTF-8 を使用） | 根本的に揃うが、古いアプリへの影響が最大 |
| D | 標準出力に日本語を出さず、結果は UTF-8 のファイルに書く | 確実だが、表示を日本語にする方針と食い違う |
| E | 一時的に変えて元の値へ戻す | C# は `CancelKeyPress` が要る。窓を閉じる ・ 強制終了で戻らない。**パイプで同時に動くと 65001 が残る（実測）** |

> [!NOTE]
> **推奨は A**: 副作用が出ず、「受け手が揃える」外部の情報とも合う。cmd 系の受け手にも渡したい C# だけ B を足す。

## 5. 検証に使ったもの

- `tests/console-cp/CpProbe.cs`: 入力・出力のコードページを表示する。`show` ・ `set` ・ `pipe` ・ `restore` ・ `restore-cancel` の 5 モード
- `tests/console-cp/ps-probe.ps1`: ps1 版。`restore`（finally で戻す）・ `redirect`（リダイレクト時だけ `SetOut`）
- `tests/console-cp/check-console-cp.cmd`: 新しい cmd の窓で実行すると、第 1 章の段 1〜6 を順に表示する。終了時に `chcp 932` で戻す
- `tests/console-cp/check-ctrl-c.cmd`: Ctrl+C で止めたときに元へ戻るかを 4 段で確かめる（C# finally ・ C# CancelKeyPress ・ ps1 5.1 ・ ps1 7）
- `tests/console-cp/check-pipe-race.cmd`: 元へ戻す処理を 2 つパイプでつないだときの窓を確かめる（`CpProbe race` を使う）
- `CpProbe io` ・ `ps-probe.ps1 io`: 3 本をリダイレクトされている分だけ差し替える（`io-none` は差し替えない）
- `tests/console-cp/check-pipe-stderr.cmd`: パイプの左右が標準エラーに日本語を出すとき、相手が窓を変えるタイミングで化けるかを確かめる（`echo-loop.cmd` を使う）
- `tests/console-cp/check-less-psh.cmd`: 受け手を less ・ psh にしたときの窓での表示
- `tests/console-cp/check-bun-node.cmd`: bun ・ node が動いている間と終了後の窓
- ビルドは .NET Framework の `csc`。.NET 7 以降での挙動は未確認
